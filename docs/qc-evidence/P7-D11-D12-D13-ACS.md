# Acceptance criteria — D12, D13, D11 item 4, D11 item 8

Written **cold** on 2026-08-21 by an independent agent against `main` at `8e4c46c`, before seeing any
implementation. Nothing in this document was written by the agent doing the work, and no source file
was edited to produce it.

Every criterion is `Given … when … then …`, and every criterion is binary. Where a criterion can only
be settled against the live Function App or the live Postgres/Prompts tables, it is tagged
**[LIVE]** — the sandbox egress is blocked from `azurewebsites.net` and the DB credentials are not
present here, so a **[LIVE]** criterion cannot be marked met by anything that ran in a sandbox.
**[SANDBOX]** criteria must be met by an executed test in `api/test/`, not by reading the diff.
**[GHA]** criteria are settled by a named GitHub Actions run id.

Two rules apply to all four items and are not repeated per criterion:

- **A source grep is not a guard.** `api/src/functions/tests/packetBuild.ts` exists precisely because
  three guards asserting that the source contained the string `ok: !failed.length && !warned.length`
  all passed while the behaviour was broken, and all failed on a rename. Where a criterion below asks
  for a guard, it means a test that calls a function with real inputs and asserts on real outputs.
  The only exception is a structural rule a runtime test cannot express (module-graph, schema
  registration, cross-file name parity) — three such exceptions are named explicitly.
- **Each item ends with "how to prove the guard is not inert":** the exact defect to reinstate and the
  named assertion that must then fail. A guard that has not been watched to fail has not been shown
  to guard anything.

## D12 — `POST /api/pipeline/run` returns 200 with `pass:false`

### The measured state at `8e4c46c`

`pipeline.ts` returns HTTP 200 on four paths, three of which carry `pass:false`:

| line | condition | status | body |
|---|---|---|---|
| 283 | `OPENAI_API_KEY` unset | **200** | `{pass:false, detail}` |
| 289 | `jobId` missing | 400 | `{pass:false, detail}` |
| 401-411 | run completed | **200** | `{pass: ids>=3 && emailsSent>=1 && warnings.length===0, urls, steps, warnings, …}` |
| 413 | anything threw | **200** | `{pass:false, detail:String(err), steps}` |

`api-test.yml` exits 1 only on `status >= 400`. A run that threw after loading the job — no documents,
no emails, `Status` left at `processing` — therefore produces `conclusion: success`.

### What the caller must be able to do — the decision

A caller must be able to tell **failure from success without parsing the body**, and must **still be
able to read the body's diagnostics when it failed**. Those two requirements are what rule out each
single-sided fix:

- **Status code alone is not sufficient.** `api-test.yml` is a *generic* vehicle — it is how every
  route in this repo is exercised. 85 `pass: false` returns exist under `api/src/functions/`, and
  `appPackets.ts` returns `{status: 200, jsonBody: {error: …}}` at seven call sites (178, 448, 527,
  561, 591, 627, 669). Fixing one route leaves the vehicle reporting green for the other 84 plus 7.
- **A workflow-side body assertion alone is not sufficient.** The console (`web/src/App.jsx:438`),
  `curl`, and any future scheduler are not GitHub Actions. A body assertion in one YAML file does not
  make the HTTP contract honest for anybody else.

**Both halves are required.** They are separable commits; neither alone closes D12.

### Criteria — route half

1. Given a `POST /api/pipeline/run` whose handler throws after the job is loaded, when the response is
   returned, then the HTTP status is outside the range 200–299. **[SANDBOX]** for the status-decision
   function, **[LIVE]** end to end.
2. Given a response body carrying `pass: false` from this route on **any** of its paths (missing
   `OPENAI_API_KEY`, missing `jobId`, caught exception, completed-but-not-clean), when the status is
   read, then it is outside 200–299 — the mapping holds for every path, not only the one reproduced.
   **[SANDBOX]**
3. Given a run that produced 3 or 4 documents but is not clean (`warnings.length > 0`, or
   `emailsSent < 1`), when the response is returned, then its status differs from the status returned
   by a run that produced **no** documents, so a caller reading only the status can tell "produced
   nothing" from "produced with warnings". **[SANDBOX]**
4. Given a run that produced documents and then failed to be clean, when the body is read, then
   `urls`, `steps`, `warnings` and `detail` are all still present and populated — a non-2xx status
   must not shrink the body to a bare error. Losing the URLs of documents that exist is a worse
   defect than the one being fixed. **[SANDBOX]**
5. Given a fully clean run (`ids.length >= 3 && emailsSent >= 1 && warnings.length === 0`), when the
   response is returned, then the status is 200 and `pass` is `true`. **[LIVE]**
6. Given an `OPTIONS` preflight to `/api/pipeline/run`, when it is handled, then it still returns 204
   with the existing CORS headers, and the new status logic does not touch it. **[SANDBOX]**
7. Given any response this route can produce, when the headers are read, then
   `Access-Control-Allow-Origin` is present — a non-2xx that drops CORS makes the console's error
   unreadable in the browser instead of merely red. **[SANDBOX]**
8. Given the decision "which status does this outcome get", when it is implemented, then it lives in
   an **exported pure function** taking the run's outcome (`docCount`, `emailsSent`, `warnings`,
   `caught`) and returning `{status, pass}`, with no `@azure/functions`, `pg`, Drive or OpenAI
   dependency — the same split as `packetBuild.summariseBuild` and `checks.ts` vs `appChecks.ts`.
   A status decision reachable only through a live Function App cannot be guarded. **[SANDBOX]**

### Criteria — workflow half (`api-test.yml`)

9. Given a response with status 200 and a JSON body containing `pass: false`, when the workflow step
   finishes, then it exits non-zero and the log states which key made it fail. **[GHA]**
10. Given a response with status 200 and a JSON body containing `ok: false`, when the workflow step
    finishes, then it exits non-zero. (`packetBuildAll` returns exactly this shape; D12's class is not
    confined to `pass`.) **[GHA]**
11. Given a response with status 200 and a top-level `error` key in the body, when the workflow step
    finishes, then it exits non-zero. **[GHA]**
12. Given a response whose body contains **none** of `pass`, `ok` or `error`, when the workflow step
    finishes, then the body assertion neither passes nor fails on it — the step's outcome is decided
    by the status alone, and the log says the body carried no verdict key. Absent evidence is
    `not_applicable`, never `pass`. **[GHA]**
13. Given a response with status in 300–399, when the workflow step finishes, then it exits non-zero.
    The current `status >= 400` test treats a redirect as success. **[GHA]**
14. Given `omit_auth: true` — the input that exists to test the **reject** path — when the API
    correctly returns 401, then the workflow does **not** exit 1. At `8e4c46c` it does, so the one
    input provided for testing rejection is permanently red and its result is uninterpretable. Closing
    D12 without fixing this makes the workflow strictly more misleading, because more paths will now
    turn red for reasons that are not failures. An explicit `expect_status` (or equivalent) input must
    carry this. **[GHA]**
15. Given a `pass: true`, status-200 response from any existing route, when the workflow step
    finishes, then it exits 0 — the assertion must be re-run against at least three previously-green
    calls (`/api/health`, `/api/config-status`, one `GET /api/app/...`) and all three must stay green.
    **[GHA]**

### Must not regress

16. Given the dev console's `approveJob` (`web/src/App.jsx:434-448`), when `/api/pipeline/run` returns
    a non-2xx status, then the console still renders `detail`, `steps` and `urls` and still marks
    MT-22 `fail` rather than falling into the network-error branch. `approveJob` never reads
    `res.ok` and `fetch` does not reject on 4xx/5xx, so the status change is expected to be
    transparent to it — this criterion requires that expectation be **checked**, not assumed. **[LIVE]**
17. Given the MT-XX harness convention (`web/src/App.jsx:375`, `data.pass === true`), when the route's
    status changes, then no other MT route's status is changed in the same commit. One route moving
    off the convention is a deliberate, documented exception; 85 routes changing at once is a
    different piece of work with a different blast radius. **[SANDBOX]**
18. Given `POST /api/pipeline/run` with no `jobId`, when it is called, then it still returns 400 — the
    one path that was already honest must not be swept into a new blanket code. **[SANDBOX]**

### How to prove the guard is not inert

Reinstate `status: 200` on the catch path of `pipelineRun` (line 413) and leave everything else in
place. The test named for criterion 2 — the one that walks every outcome the pure status function can
produce and asserts `pass === false ⇒ status ∉ [200,299]` — must fail on the caught-exception case.
For the workflow half: run `api-test.yml` against a route that returns `{ok:false}` at 200
(`POST /api/app/opportunity/<id>/packet/build-all` on an opportunity with no Google token) and the
step must exit non-zero; revert the assertion and the same run must go green. Record both run ids.

## D13 — `Promise.all(docJobs)` orphans Google Drive files

### The measured state at `8e4c46c`

`pipeline.ts:345-351` builds an array of 3 or 4 `copyAndInject(...)` promises. They are **eager** —
each has already issued its Drive `files/{id}/copy` by the time `Promise.all` is awaited.
`Promise.all` rejects on the **first** rejection and does not cancel the others; the survivors keep
running, resolve to ids, and those ids are unreachable — the `catch` at line 413 has no handle on
them. Worse, `copyAndInject` returns the id **only on full success**: if `batchUpdate` throws at line
42, the copy at line 31 already succeeded and its id dies inside the function, invisible even to a
correctly-written `allSettled` caller.

`grep -rn "method: 'DELETE'" api/src` → three hits, all Microsoft Graph subscription deletes
(`mailWatch.ts:527, 997, 1215`). **There is no Drive DELETE anywhere in `api/src`.** Confirmed in
sandbox, not inherited from the D13 row.

`appPackets.renderArtifact` orphans one more file on **every** rebuild (`doc_url` is overwritten; the
superseded id is returned as `supersededDocUrl` for the caller to record, and nothing deletes it).
D13 is not confined to `pipeline.ts`.

### Criteria — enumerability (the part the row says is structural)

19. Given a run in which the second of four `copyAndInject` calls fails at its **copy** step, when the
    failure is handled, then the ids created by the other three are present in the handler's failure
    report — no created id is discarded because a sibling rejected. **[SANDBOX]**, via an injectable
    `fetch`.
20. Given a `copyAndInject` call whose copy **succeeds** and whose `batchUpdate` **fails**, when the
    failure is handled, then the id of the file that was created is present in the failure report.
    This is the case a naive `allSettled` still loses, because the rejected promise carries an `Error`
    and not an id. **[SANDBOX]**
21. Given any run that reaches the document stage, when the handler returns for any reason, then no
    Drive copy started by that run is still in flight — the handler awaits **all** settled outcomes,
    never the first rejection. **[SANDBOX]**
22. Given a run in which every document job fails at the copy step, when the failure is handled, then
    the reported created-file set is empty and the run does not claim to have cleaned up anything.
    Reporting a cleanup that had nothing to clean is how a cleanup path goes green while broken.
    **[SANDBOX]**

### Criteria — what happens to the enumerated files

23. Given a set of ids created by a run that then failed, when the run finishes, then every id in that
    set has been **either** deleted from Drive **or** persisted to a queryable store with the run's
    identifier, the template it came from, and the timestamp. Silently dropping the ids fails this
    criterion regardless of which branch is chosen. **[SANDBOX]** for the branch logic; **[LIVE]** for
    the effect.
24. Given the delete branch is chosen, when a delete is issued, then a subsequent `GET` of that file
    id returns 404 or reports the file trashed. A `fetch` that resolved is not proof of a delete.
    **[LIVE]**
25. Given the delete branch is chosen and the OAuth token lacks Drive delete scope, when the delete is
    attempted, then the run reports a **named configuration error** identifying the missing scope, and
    the ids fall through to the record branch rather than being dropped. A 403 from Drive must not
    become a silent skip. **[LIVE]**
26. Given a cleanup (delete or record) that itself fails, when the run returns, then the **original**
    error is still the reported cause and the cleanup failure is reported alongside it. A cleanup
    failure that masks the failure that triggered it turns one defect into two. **[SANDBOX]**
27. Given the record branch is chosen, when the ids are persisted, then the store is queryable by a
    `db-query.yml` SQL statement written into the evidence, and that query is run once and its output
    recorded. An orphan population nobody can query is one nobody can ever clean up
    (`appPackets.ts:398-403`, the same conclusion reached for `supersededDocUrl`). **[LIVE]**

### Criteria — partial success, and the decision it forces

28. Given a run in which 3 of 4 documents built and the 4th failed, when the run returns, then the 3
    successful documents are **retained** and their URLs are returned. Rolling back a usable resume
    because the cover letter failed destroys work the operator can use, and the compact ATS resume is
    already an optional fourth document that the run is designed to proceed without. **[SANDBOX]**
29. Given such a partial run, when the `JobApplications` row is updated, then **no** URL field is
    written for a document that does not exist, and `Status` is not set to `complete`. At `8e4c46c`
    the update at line 361-366 is unreachable on this path (the throw escapes first), leaving `Status` at
    `processing`; whichever way the fix goes, the row must not end up claiming four documents when
    three exist. **[SANDBOX]**
30. Given a retained partial run, when the response is returned, then `pass` is `false` and the status
    is the non-2xx code D12 criterion 3 assigns to "produced with warnings". D13's partial-success
    decision and D12's status mapping must agree; if they are implemented in different commits, the
    second one lands with a test asserting the pair. **[SANDBOX]**

### Criteria — no multiplication (the X5 trace P7-ACCEPTANCE demands)

31. Given a failed run that is retried, when the retry finishes, then the number of Drive files
    attributable to the two attempts is not greater than the number a single successful run creates,
    plus the recorded/deleted orphans of the first — a retry must not silently double the leak.
    **[SANDBOX]** by counting copy calls against an injectable `fetch`.
32. Given the remediation loop's contract that rendering happens **once** at the end of an N-pass loop
    (P3-25, guarded by `H35`), when D13's retry or cleanup logic is added, then `H35` and `H35b` still
    pass — no Drive call may be introduced into the loop body by a cleanup path. **[SANDBOX]**
33. Given `renderArtifact`'s existing per-rebuild orphan (`supersededDocUrl`), when D13 is closed,
    then either that id flows into the same enumerate-and-handle mechanism, or the D13 row records in
    writing that it does not and `.claude/DEFERRED.md` keeps a row for it. Closing D13 while the
    product's real render path keeps orphaning one file per rebuild, with no row saying so, is the
    failure mode `DEFERRED.md` exists to prevent. **[SANDBOX]**

### How to prove the guard is not inert

Two reinstatements, both required, because they fail different assertions:

1. Change the orchestration back to `Promise.all(docJobs)` and leave `copyAndInject` as fixed. The
   test named for criterion 19 — four jobs, the second's copy stubbed to HTTP 500 — must fail,
   reporting that only 0 of the other 3 ids were enumerated.
2. Restore `copyAndInject` to returning the id only on success (delete the out-of-band report of the
   id between the copy and the `batchUpdate`), keeping `allSettled`. The test named for criterion 20 —
   copy stubbed to 200 with an id, `batchUpdate` stubbed to 500 — must fail, because the created id is
   absent from the report while the file exists.

A fix that passes test 1 and not test 2 is the half-fix D13 explicitly warns about.

## D11 item 4 — the "duplicate 29k prompt" claim

### What is actually established at `8e4c46c`, and what is not

The claim rests on **equal lengths**, in four places that all cite the same measurement and none of
which compared content: `docs/qc-evidence/P7-ACCEPTANCE.md:37`,
`docs/qc-evidence/prompts/ats_system.md` (the length table, api-test run `32315571687`),
`.claude/QC-EVIDENCE-PLAN.md:121` ("byte-identity **inferred** from equal length"),
`.claude/memory.md:1325`, `.claude/actions.md:965`, and `docs/zap-289877647/README.md:34`.

Live lengths, measured 2026-08-20: `resume_user` **29068**, `portfolio_user` **29068**,
`resume_system` **329**, `portfolio_system` **329**.

**Measured in this sandbox while writing these criteria** (not previously in the repo's evidence), the
zap that seeded the table is in-repo and its two prompt nodes are *not* the same size:

| zap node | file | `user_message` chars |
|---|---|---|
| 289877661 → `resume_user` | `docs/zap-289877647/prompts/16-…md` | **29,070** |
| 299599701 → the second call's prompt | `docs/zap-289877647/prompts/17-copy-…md` | **7,713** |

The two share a **330-character** common prefix and then diverge (node 16: "14 structured sections…";
node 17: "structured sections…"). So the live `portfolio_user` length matches the **resume** node to
within two characters and is nearly 4× the portfolio node. That is strong evidence for the bad-seed
story and it is available without touching Azure — but it is still a length argument, and CLAUDE.md's
ground-truth rule forbids resolving "which is right" from a proxy. It raises the prior; it does not
establish the fact.

### Criteria — establishing the fact (must complete before any authoring)

34. Given the live `Prompts` table, when the fact is established, then the evidence is a **SHA-256
    digest of the `content` string** of each of `resume_user`, `portfolio_user`, `resume_system` and
    `portfolio_system`, recorded in the evidence document alongside the Actions run id that produced
    them. A length comparison, a diff of lengths, or a restatement of the 29068 figure does not
    satisfy this criterion. **[LIVE]**
35. Given those four digests, when they are recorded, then the record states explicitly for each pair
    whether the two digests are equal, and the sentence "inferred from equal length" appears nowhere
    in the new evidence. **[LIVE]**
36. Given the live `portfolio_user` content, when the fact is established, then it is also compared
    against **both** zap nodes (16 and 17) — the primary source both live rows derive from — and the
    comparison states which node it matches. Comparing the two live rows only tells you they are the
    same; it never tells you which one is wrong. **[LIVE]** for the live side, **[SANDBOX]** for the
    node extraction.
37. Given the digest capture is run through `api-test.yml`, when it runs, then the workflow log does
    not need to contain four full 29k prompt bodies for the digests to be read — the digest is
    computed where the content is, not by dumping 120KB into a job log a human must scroll.
    **[GHA]**

### Criteria — branch A: the digests are equal (claim CONFIRMED)

38. Given the two digests are equal, when a remedy is chosen, then the installed `portfolio_user`
    content is **traceable to `docs/zap-289877647/prompts/17-copy-update-resume-portfolio-fields-prompt.md`**
    — the prompt that the migration was supposed to install — and the evidence names the file and the
    transformation applied to it. Authoring a new prompt from scratch when the intended one is in the
    repo is the "Extend, don't duplicate" violation in its purest form. **[SANDBOX]**
39. Given a candidate `portfolio_user` content, when it is installed, then it has **first** been
    checked to emit what Call 2's consumer parses: `pipeline.ts:208` runs
    `parseAgentJson(r2.choices?.[0]?.message?.content)` and falls back to Call 1 when it gets no JSON
    object. `ats_system` v001 is the recorded precedent — its stored `ats_user` counterpart instructed
    `###` sections and raw HTML while the code `JSON.parse`d the reply, so `c3` was `{}` on **every**
    run and all 29 rows of `swap_decision` read `kept | unattributed` (db-query run `32315894903`).
    Installing a prompt with the wrong output contract converts a duplicated prompt into an inert
    call, which is worse and much harder to see. **[SANDBOX]** for the contract review, **[LIVE]** for
    the behaviour.
40. Given the new prompt is installed, when a real packet build runs, then the response's `warnings`
    array does **not** contain `Call 2 (portfolio) returned no JSON object`, and the portfolio/cover
    merge fields in the resulting `pkg` are non-empty. A 200 with the fields empty is a result to
    investigate, not a pass. **[LIVE]**
41. Given the install goes through `POST /api/prompts`, when it completes, then `GET /api/prompts`
    shows `portfolio_user` at `version: 2, is_active: true`, and v001 still exists — the route
    deactivates rather than destroys, and the rollback is the same call with the previous content.
    **[LIVE]**
42. Given the new prompt is active, when a build runs, then `promptVersions['portfolio_user']` in the
    build output reads 2 — proof the pipeline consumed the new row rather than a cached or hardcoded
    fallback. `buildPackageForJD` already returns `promptVersions`; this criterion requires it be
    **read**, not merely returned. **[LIVE]**
43. Given the claim is confirmed, when the item is closed, then every place that carried the
    length-based version of the claim is updated to the digest-based one: `P7-ACCEPTANCE.md:37`,
    `QC-EVIDENCE-PLAN.md:121`, `actions.md:965` (C1), `memory.md:1325`,
    `docs/zap-289877647/README.md:34`, and `docs/qc-evidence/prompts/ats_system.md`'s table.
    Fix-all-consumers applies to claims as much as to constants. **[SANDBOX]**

### Criteria — branch B: the digests differ (claim FALSE)

44. Given the two digests differ, when the item is closed, then **no prompt is authored and no prompt
    is installed**, and the item moves to a "won't do" line quoting both digests as the reason.
    **[SANDBOX]**
45. Given the claim is false, when it is retired, then the same six locations listed in criterion 43
    are corrected, each carrying the digests. A false claim left standing in five documents while
    being retired in one is how this class of defect survives. **[SANDBOX]**
46. Given the claim is false, when the evidence is written, then it also states what the equal lengths
    **were** — two prompts of exactly 29,068 characters that are not the same text is itself a fact
    worth recording, and the next reader will otherwise re-derive the same suspicion. **[SANDBOX]**

### Criteria — the standing guard (both branches)

47. Given two `Prompts` rows whose active content is byte-identical, when `buildPackageForJD` runs,
    then it emits a warning naming both partition keys, and that warning travels the same path as the
    existing ones (into `warnings`, therefore into `ensurePackage`, `summariseBuild` and the response).
    **The invariant, not the incident: the pipeline must never silently run two distinct agent calls
    on the same prompt text.** This guard would have caught the original seed and will catch the next
    one, in either branch. **[SANDBOX]**
48. Given two rows that differ by a single character, when the same check runs, then it emits nothing.
    A guard that fires on near-duplicates is a cry-wolf guard; this comparison is exact-equality, never
    similarity — fuzzy matching is for ranking, never for accusing. **[SANDBOX]**
49. Given the four prompt rows are absent from the table entirely (a fresh or unreachable store), when
    the check runs, then it reports `not_applicable` and does **not** report "no duplicates found".
    Absent evidence is never a pass. **[SANDBOX]**

### How to prove the guard is not inert

Call the criterion-47 check with a fixture whose `resume_user` and `portfolio_user` strings are equal
and assert it names both keys; then change one character in one of them and assert it names nothing;
then delete both keys from the fixture and assert `not_applicable`. Run all three. The middle and last
assertions are what stop this becoming the eighth guard in this repo that fires on correct code.

## D11 item 8 — hardcoded Drive template ids and single-tenant Graph sender

### The measured state at `8e4c46c`

Two independent copies of the same four literals:

| constant | `pipeline.ts` | `packetTemplates.ts` |
|---|---|---|
| `RESUME_TEMPLATE_ID` | 20 | 13 |
| `PORTFOLIO_TEMPLATE_ID` | 21 | 14 |
| `COVER_LETTER_TEMPLATE_ID` | 22 | 15 |
| `OUTPUT_FOLDER_ID` | 23 | 16 |

plus `mt05.ts:11-12`, `mt06.ts:11-12`, `mt18.ts:17-18`, `diagDocStructure.ts:3` (legacy MT harness).
Graph sender: `pipeline.ts:387` `users/dev@enterpriseds.io/sendMail`, also `mt07.ts:20`, `mt21.ts:70`,
`mt47.ts:6`. Recipient fallback: `pipeline.ts:300` `job.SendToEmail || 'von.ellis@enterpriseds.io'`.

`CONFIG_KEYS` (`pipelineConfig.ts:22-27`) lists four keys. The console writes RowKeys as
`${config.id}.${field.key}` (`web/src/App.jsx:679-680`) and already offers, at lines 46-71:
`microsoft.senderEmail`, `microsoft.recipientEmail`, `google.outputFolderId`,
`google.resumeTemplateId`, `google.portfolioTemplateId`, `google.coverLetterTemplateId`,
`google.compactResumeTemplateId` (the only one already read), `google.videoFolderId`.

### The criterion that decides this item

**The production path does not go through `pipeline.ts`'s constants.** The Executive Engine renders
via `appPackets.renderArtifact` → `metaFor(art.type).templateId` → `packetTemplates.TEMPLATE_META`, a
module-level constant, and `copyTemplate` hardcodes `parents: [OUTPUT_FOLDER_ID]` at
`packetTemplates.ts:57`. A fix confined to `pipeline.ts` leaves **the product** on hardcoded ids while
making the settings screen appear to work — which is precisely the failure P7-ACCEPTANCE names: *a
setting that exists and is not read is worse than one that does not exist.* Criterion 53 is the one
that must not be waived.

### Criteria — the settings are read

50. Given `google.resumeTemplateId` is set in `AppConfig`/`auth`, when `POST /api/pipeline/run` builds
    the full resume, then the Drive copy is issued against that id and not against
    `1bwOcxvkbihRTUjOzVjrWSPnDomwqy6gOz6229mdzbZw`. **[SANDBOX]** via an injectable `fetch`;
    **[LIVE]** for the effect.
51. Given each of `google.portfolioTemplateId`, `google.coverLetterTemplateId` and
    `google.outputFolderId` is set, when the run builds, then each is used for its corresponding copy
    and for the `parents` of every copy respectively. Each of the four is asserted **separately** — a
    test that sets all four at once cannot tell which of them is actually wired. **[SANDBOX]**
52. Given `microsoft.senderEmail` is set, when a delivery email is sent, then the Graph URL is
    `users/<that value>/sendMail`. Given `microsoft.recipientEmail` is set and the job row carries no
    `SendToEmail`, then that value is the recipient. **[SANDBOX]**
53. Given `google.resumeTemplateId`, `google.portfolioTemplateId`, `google.coverLetterTemplateId` and
    `google.outputFolderId` are set, when the **product** path runs — `appPackets.renderArtifact` for
    each of `resume`, `compact_resume`, `portfolio`, `cover` — then every Drive copy and every
    `parents` value comes from the configured values. `TEMPLATE_META` may no longer supply a
    `templateId` from a module constant at the point of the copy. **[SANDBOX]**

### How to prove the guard is not inert

Three reinstatements, one per class of defect:

1. Revert `renderArtifact`/`copyTemplate` to reading `TEMPLATE_META[type].templateId` and the module

3. Restore the seed literal as an unconditional fallback when a config row is present but rejected.
   The test named for criterion 59 must fail.
