6. Defects and fragilities found in the export

Broken reference. Step 22 reads 289877663__output__Item 44–55, but node 289877663 is absent from the export. Steps 22–23 therefore produce nothing usable, and nothing downstream reads them — the HTML-cleanup branch is dead.
Everything is paused. All 39 non-trigger nodes carry paused: true while the zap status is on. The baseline describes intent, not a currently-running pipeline.
  • Storage key collisions. Steps 6, 7, 8 all write the key Current Expertise; steps 11 and 15 both write Executive Profile Paragraph. Prompts read by node id (__value) so they still get the right text, but the storage table itself is unreliable as a source of truth.
  • Positional coupling. Content is addressed as Item 3 … Item 55 after splitting on ###. Any prompt change that adds, drops or reorders a section silently shifts every downstream field, including which text lands in which resume slot.
  • Concatenated split. Step 19 splits the joined output of steps 17 and 18, so the two prompts' section counts are load-bearing on each other.
  • Memory key is hour-based. {{form id}}{{hour}} means two runs of the same form in one hour share conversation memory, and a run that crosses the hour boundary loses it mid-chain.
  • Duplicate generation. Steps 17 and 18 are near-identical 16k-token calls; step 20 converts skills to HTML and step 28 converts them back to plain text.
  • Unvalidated fallback. Unknown from step 2 is passed straight to Google Docs as a folder id in step 37.
  • Single-tenant constants. "Von Ellis" in document titles, one hardcoded Engineering template folder in step 36, and role routing that only knows Engineering and Product Management.
  • Dead input. Step 13 Soft/Hard Skills (~2,871 chars) is never read.
  • No failure path. No retries, no validation that any Item N exists, no notification when a document or an LLM call fails; the email is the only signal that the run happened.
  • Model and temperature. All five calls use gpt-4o-mini at temperature 1.0, including the QA reconciliation step.
  • Editor warnings. Nodes 20, 22, 26 and 40 carry has_automatic_issues: true; node 40's body also contains a stray <-- inside the table markup.

7. What this implies for the migration

The workflow is three things stacked: a profile store (steps 3–15), a generation pipeline (17–35), and a review surface (40). Only the middle third was migrated to the app's Prompts table; the profile store is still hardcoded workflow steps, and the review surface is still an email.

The QA/QC list in section 5 is what the review surface has to become: sixteen checks, of which four (Q2, Q3, Q4, Q5) already produce structured per-item evidence that is being thrown into an email table, and nine produce no evidence at all. Making them UI-visible means giving each one a pass/fail state and a place to show its reasoning, which in turn means the pipeline has to persist what it currently only prints.
