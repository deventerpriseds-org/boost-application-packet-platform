## 1. What the sources actually say

### 1.1 `docs/qc-evidence/BACKLOG.md` §P8.1 (lines 363-374), verbatim

> ### P8.1 Auto-correct before reporting (R1)
> - [ ] Anything the rules engine can fix deterministically is fixed in the generated text before the
>       user sees it, and written to a `correction` row: `artifact_id`, `section_id`, `phrase`,
>       `replacement`, `reason`, `source` (`profile_figure` | `generalized`), `reverted_by`,
>       `reverted_at`.
> - [ ] The UI presents corrections as a change log in finished framing, with per-correction Undo and
>       "suggest something different". Reverting restores the original string in place.
> - [ ] Corrections never count toward the fix/review counters; they have their own count.
>
> **Acceptance:** a packet whose only problems are auto-correctable reaches the user with zero open
> items and a non-empty change log; undoing a correction restores the exact original substring and
> re-opens the corresponding check.

The middle bullet and the third bullet are this lane. The first bullet is the API lane.

### 1.2 `docs/qc-evidence/BACKLOG.md` §P8.6 (lines 417-425), verbatim

> ### P8.6 Ad-hoc correction affordances (R6)
> - [ ] Per-field "ask for a change" scoped to that merge field.
> - [ ] `Show original` on every field including static template blocks (which render their real
>       template text and merge placeholders).
> - [ ] Keyword-level controls: put back the item it displaced, swap for another skill from the
>       profile's bank, or drop it and leave the posting line open — each recording the coverage
>       consequence.
>
> **Acceptance:** a user can correct any field they happen to notice without going through the QC

**A note on scope, stated rather than papered over.** The lane I was given is "correction
affordances / the change-log UI". The backlog's P8.6 bullets and the backlog's P8.1 *UI* bullet are
two overlapping halves of the same screen, and the third P8.6 bullet ("keyword-level controls …
each recording the coverage consequence") **cannot be satisfied in `app/` alone** — "dropping a
keyword lowers coverage" is a write that changes a stored coverage number, and there is no route
for it. So the ACs below cover: the change log (P8.1 UI bullet), the separate corrections count
(P8.1 counting bullet), and the per-field ad-hoc affordances (P8.6 bullets 1-2) **as far as `app/`
can carry them without a stub**. §7 says exactly which parts are left for the API lane. Do not read
a green run of these ACs as P8.6 closed.

### 1.3 `docs/qc-evidence/SPEC.md` §2, ground rules R1, R4, R5, R6, verbatim

> **R1 — Correct, then report.** Anything the system can fix, it fixes before the user sees it, and
> records the fix. The user reviews a change log, not a to-do list. Framing is finished
> ("Corrected", "Changes made"), never pending ("needs fixing"). Only what genuinely cannot be
> settled without the user appears as an open item.

> **R4 — One source per number.** Any two counts describing the same population must be computed
> from the same list with the same filter. Fixes and reviews are always counted separately and
> labelled ("1 to fix · 3 to review"), never merged into one ambiguous number.

> **R5 — Every count deep-links.** A badge that says "1 to fix" opens the exact field it refers to,
> scrolls to it and outlines it. No number is a dead end.

> **R6 — Ad-hoc correction over batch approval.** The user should be able to change anything they
> happen to notice, in place, scoped to the field they are looking at — not only the items the
> system flagged.

> Then two lists, **on the page, not behind a tab or a search**:
>
> 1. **Done for you** — "15 corrections already applied · change or revert any of them". Each row:

### 1.7 The API contract this UI must render, read-only from the unmerged branch

`git show origin/claude/qc-p8-1-corrections:api/src/functions/tests/correction.ts`. The row shape:

```ts
export interface Correction {
  merge_field: string
  phrase: string          // the exact original substring being replaced
  replacement: string     // what it becomes
  char_start: number      // offsets into the ORIGINAL field text
  char_end: number
  before_sha256: string   // SHA-256 of the whole ORIGINAL field text
  applied_seq: number     // "Ascending by char_start, so a change log reads in document order."
  reason: string
  source: CorrectionSource   // 'profile_figure' | 'generalized'
}
```

And the revert, whose refusal is a first-class result, quoted verbatim:

```ts
export interface RevertResult {
  ok: boolean
  text?: string
  /** Why the revert was refused. A refusal writes nothing. */
  reason?: string
}
```

> Undo ONE correction, leaving the others applied.
>
> Refuses rather than guesses. If the field was rewritten since — a later pass, a manual edit —
> the recovered original will not hash to `before_sha256` and this returns `ok:false` with a reason.
> Writing a best-effort splice into a document nobody can check is worse than declining.

Two refusal strings the module actually returns, which this UI must be able to render:
`no applied correction with seq ${seq}`, and
`this field was edited after the correction was applied, so the original cannot be restored safely`.

Note the field list against the backlog's: the API contract has **`merge_field`, `char_start`,
`char_end`, `before_sha256`, `applied_seq`** which the backlog bullet does not name, and does **not**
have `section_id`, `reverted_by` or `reverted_at` on the pure interface (those are row/table
columns, not part of the planning shape). An implementer who codes the UI against the backlog's
field list will not find `applied_seq` and will invent an ordering. AC-13 exists for that.

## 4. Acceptance criteria

Format: `Given <context>, when <action>, then <observable outcome>.` Each is binary.
"Works correctly" appears nowhere below.

**Where** uses only what §2 measured as runnable:
`unit` = `npm --prefix app test` · `qc` = `npm --prefix app run test:qc` ·
`browser` = `npm --prefix app run test:browser` · `blocks` = `npm --prefix app run test:blocks` ·
`build` = `npm --prefix app run build`.

### A. The payload, and the states that must not collapse into one

**AC-1 — the change log and the counters read ONE payload object.**
Given a single `checks-result` payload for an artifact, when the change log and the
"n to fix · n to review" strip both render, then both derive from that one `result` value handed
down as a whole, and the component issues no second fetch for corrections. If the implementer
instead puts corrections on a separate endpoint (the `artifactInsertions` precedent), then
`reconcile(result)` is extended to REPORT a disagreement when the two payloads describe different
runs (`run_id` / `computedAt` differ) and a test proves that branch fires — silently rendering both
is the FAIL.
**Where:** `unit` (a fixture drives both derivations; a grep asserts `QcRail.jsx` /
`AssetGateDrawer.jsx` reach corrections only through the one payload prop).

**AC-2 — the corrections list and any corrections COUNT the server sends are reconciled, never
silently reconciled-away.**
Given a payload carrying `corrections: [3 rows]` and a server-sent count of `5`, when the surface
renders, then the disagreement is REPORTED through `reconcile()`'s existing mechanism (assetGate.js:162,
"the server counted N finding(s) needing attention but sent M such row(s)") rather than one of the
two numbers being quietly chosen.
**Where:** `unit`.

**AC-3 — the count is the length of the list that is displayed.**
Given the rendered change log lists N rows, when the corrections count is read from the DOM, then it
equals N — the number and the list are the same population computed once (R4).
**Where:** `unit` + `qc`.

**AC-4 — absent, empty, unchecked and malformed are FOUR rendered states, never one.**
Given four payloads for the same artifact — (a) `gate: null` (never checked), (b) `gate: 'pass'`
with **no `corrections` key at all** (the live shape today, per M2), (c) `gate: 'pass'` with
`corrections: []`, (d) `gate: 'pass'` with `corrections: 7` or `corrections: null` — when each is
rendered, then the four produce four **pairwise different** non-empty strings, and:
- (a) says the checks have not been run, so there is no change log — **not** "no corrections";
- (b) says the server sent no change log with this run (this build of the API does not report
  corrections) — **not** "no corrections";
- (c) says nothing needed correcting;
- (d) says the payload's `corrections` was not a list, naming the type observed.

**"The server did not send a change log" and "the server sent an empty change log" are different
facts about the world. Rendering both as "no corrections" is this feature's vacuous green** — the
same class as P8.1's AC-14, and per `CLAUDE.md`, "Absent evidence is `not_applicable`, never `pass`."
**Where:** `unit` (four fixtures; assert six pairwise `notEqual`s on the returned strings) + `qc`
(assert four distinct rendered bodies).

**AC-5 — the selector decides absent-vs-empty BEFORE any normalisation.**
Given the exported selector (`correctionsState(result)` or whatever it is named), when it is called
with `{corrections: undefined}` and with `{corrections: []}`, then it returns different `kind`
values, and it reaches that decision from the raw property — **not** from a value that has passed
through `arr()`, which is `Array.isArray(v) ? v : []` (assetGate.js:247) and maps `undefined`,
`null`, `7` and `[]` all to `[]`. A source grep asserting `arr(` is not applied to `corrections`
before the `kind` is decided is acceptable here; this is a structural invariant a runtime test alone
cannot pin, per the H-case rules in `CLAUDE.md`.
**Where:** `unit`.

**AC-6 — the absent state is not a spinner and not an error.**
Given payload (b) of AC-4 (loaded successfully, `resultLoading: false`, `resultError: null`, no
`corrections` key), when the surface renders, then it renders neither a loading state nor an error
state — it renders the settled statement that this build of the API does not report corrections.
**Where:** `unit` + `qc`.

**AC-7 — the absent state does not claim a number.**
Given payload (b), when the counts strip renders, then **no** corrections number is printed at all —
not `0`, not `—`, not `n/a`. Zero is a measurement, and reporting a measurement that was never taken
is the exact shape of the bug this whole feature is against (the `verdictLine` precedent,
qcRail.js:251: "A null verdict means the reviewer HAS NOT RUN. '0 disagreements' is a measurement").
**Where:** `unit` (the selector returns `hasNumber: false`) + `qc` (assert the hook is absent from
the DOM, not merely that it reads `0`).

### B. R4 — one source per number; corrections never enter the attention counters

**AC-8 — corrections cannot move the fix/review numbers.**
Given payload P with 1 deterministic `warn` and 0 reviewer findings, and payload P' byte-identical to
P except that it also carries 7 corrections, when both are measured, then
`railCounts(P)` deep-equals `railCounts(P')`, every field of `attentionSplit(P)` equals
`attentionSplit(P')`, `railAttention(P) === railAttention(P')`, and `railTotals([P])` differs from
`railTotals([P'])` in the corrections field and **in no other field**.
**Where:** `unit`. *This is the AC that catches corrections leaking into the counters.*

**AC-9 — three numbers, three labels, three hooks (P8.1 AC-7, `app/` half).**
Given an artifact with 3 corrections and 1 open `warn`, when the counts strip renders, then the DOM
carries the "to review" number and the "corrected" number as **two distinct elements with two
distinct `data-qc` hooks and two `data-qc-n` values**, each labelled with what it counts (SPEC §7:
"Say what a number counts"), and `railCounts().toFix` is `0` while `railCounts().toReview` is `1`.
**Where:** `unit` + `qc`. *This is P8.1 AC-7 restated so it is provable without `ui-verify.yml`.*

**AC-10 — nothing sums them.**
Given the three numbers, when `qcRail.js`, `assetGate.js`, `QcRail.jsx` and `AssetGateDrawer.jsx` are
read, then no exported object carries a `total`, and no rendered element prints a value equal to any
sum of two of the three. A guard asserts no arithmetic combines the corrections field with either
counter.
**Where:** `unit`.

**AC-11 — the corrections number comes from the same payload as the counters (P8.1 AC-7, second
half).**
Given the one `result` object, when the corrections number and the fix/review numbers are traced,
then all three are functions of that object alone, with no second source, no prop drilled from a
different fetch and no component-local state.
**Where:** `unit` (grep + a fixture proving all three change together when the one payload changes).

**AC-12 — one definition, and every surface that prints the number uses it.**
Given the implementer names the set of surfaces that print a corrections number, when the source is
read, then (i) every one of them obtains it by calling the ONE exported selector, (ii) **no `.jsx`
anywhere in `app/src/` touches `.corrections` except through that selector** — in particular no
`arr(result.corrections).length` inline — and (iii) any surface that deliberately does NOT print the
number (e.g. `GateBadge`, if that is the choice) is asserted to render no corrections hook, so its
omission is a decision on the record rather than an oversight.
`GateBadge` is rendered by `Library.jsx`, `OppDetail.jsx` and `PacketBuilder.jsx` as well as the
drawer, so a number added in `qcRail.js` only reaches one of four surfaces.
**Where:** `unit` (`grep -rn "\.corrections" app/src/` and assert every hit is in the one module).
*This is `CLAUDE.md`'s "Fix all consumers" rule made binary. §6.2 is what it catches.*

**AC-13 — R5: the corrections count deep-links, or is inert WITH a reason.**
Given a corrections count of N, when it is activated, then it lands on a visible destination: each
row's `merge_field` resolves to a rendered block in the drawer's `blocks` tab (the `focusField` deep
link, AssetGateDrawer.jsx:129) and the target is scrolled to and outlined. Given a correction whose
`merge_field` resolves to no rendered block, then that row is rendered **inert with its reason**
(the `QC_HOOKS.countInert` precedent, qcRail.js:48 — "an offender that resolves to no section"), and
is **not** a button that does nothing.
**Where:** `unit` (the resolution function, both branches) + `qc` (click, then assert the target
block is present and carries the outline class).

### C. Rendering the change log honestly (R1)

**AC-14 — document order, decided by the module.**
Given rows arriving in payload order `applied_seq` 3, 1, 2, when the log renders, then they appear
1, 2, 3 — ascending `applied_seq`, which the API contract defines as ascending by `char_start`
"so a change log reads in document order" — the ordering is performed by an exported function, and
`QcRail.jsx` / `AssetGateDrawer.jsx` contain no `.sort(` over corrections.
**Where:** `unit` + `qc`.

**AC-15 — rows with a duplicate or missing `applied_seq` are surfaced, not silently ordered.**
Given two rows both carrying `applied_seq: 1`, or a row with `applied_seq: undefined`, when the log
renders, then the ordering is still deterministic (stable in payload order within an equal weight,
per `bySeverity`'s precedent at qcRail.js:168) and the anomaly is reported rather than hidden. A
non-deterministic order across two renders of the same payload is a FAIL.
**Where:** `unit` (render the same fixture twice, assert identical order).

**AC-16 — every row shows what changed, why, and where.**
Given a row `{merge_field:'ResumeSummary', phrase:'$18M', replacement:'8-figure', reason:'the
posting states $18M; your profile does not evidence it', source:'generalized', applied_seq:1}`, when
it renders, then the DOM contains: the original `$18M` marked as replaced, the replacement
`8-figure`, the `reason` **verbatim**, the field's plain-language label from `fieldLabel()`, and the
raw merge-field name (SPEC §4.5: "the real merge-field name in mono"). No field of the row is
dropped, and no field is reworded.
**Where:** `qc`.

**AC-17 — finished framing, asserted on the rendered strings.**
Given any correction row and the change log's own headings, when the strings the module returns are
read, then they use finished framing ("Corrected", "Changes made", "already applied") and contain
**none** of: "needs fixing", "to fix", "to do", "pending", "action required", "you should". The
guard asserts the STRINGS a function returns, not that a constant is named a certain way (AC-32).
**Where:** `unit` + `qc` (assert on the rendered body text of the change-log region).

**AC-18 — `source` is rendered, and an unknown value falls through to itself.**
Given `source:'profile_figure'`, the row states the replacement came from the user's own profile;
given `source:'generalized'`, it states the figure was generalised because the profile does not
evidence one; given any third value, it renders that raw value rather than defaulting to either of
the two known ones (the `assetLabel` precedent, assetGate.js:48 — "An unknown type falls through to
the raw type - never to a blank"). Defaulting an unknown source to `generalized` is a FAIL: it would
tell the reader a number came from nowhere when the server said otherwise, or the reverse.
**Where:** `unit`.

**AC-19 — no fabricated data, anywhere in `app/src/`.**
Given `app/src/**`, when grepped, then it contains no literal correction row, no literal phrase,
replacement, reason, count or merge-field name used to populate the change log — every value
rendered comes from the payload. Fixtures exist only under `app/test/**`. Given the payload is
absent or empty, the surface renders the honest state of AC-4 and no placeholder rows.
**Where:** `unit` (the `no fixture data backs the remediation tab` precedent, qcRail.test.mjs:520:
"the loops tab must read a real query, never a literal").

### D. Undo, "suggest something different", and the refusal state

**AC-20 — NO DEAD UI: the Undo control is wired to a real route, or it is not rendered.**
Given that no revert route exists (M2), when the change log renders, then **either**
(a) no Undo control is rendered at all and the log states in the UI that it is read-only in this
build, **or** (b) an Undo control is rendered that calls a real `api.js` helper against a real
route. A control whose handler is `toast(...)`, `alert(...)`, `() => {}`, a `console.log`, or that
renders "coming soon" / "not yet available" as a button label is a **FAIL** — `CLAUDE.md`: "Never
ship a `onClick={() => toast('...')}` stub as a real button. … If a feature isn't ready, hide the
control — don't fake it."
The guard inspects the HANDLER, not the label.
**Where:** `unit`. *Given M2, (a) is the only honest option this lane can take; §7 records why.*

**AC-21 — the api.js owner rule, both directions.**
Given a corrections helper is added to `api.js`, when its line is read, then: a GET carries
`?owner=` / `&owner=` (without it `resolveOwner()` silently falls back to the demo owner and 404s the
real owner's rows — the `listPersonas` failure); and the revert POST carries **no** `?owner=`,
because `requireWrite()` / `resolveOwner()` take the owner from the verified session and ignore
`?owner=` entirely (api.js:174-178 states exactly this). And: the change-log component contains no
`fetch(` of its own — it goes through `api.js`, "which is where the owner rule lives"
(qcRail.test.mjs:578).
**Where:** `unit` (line-level grep, extending the existing test at qcRail.test.mjs:568).

**AC-22 — a refusal is a rendered state, not a swallowed error (the state P8.1 AC-11 implies).**
Given the revert path returns `{ok:false, reason:'this field was edited after the correction was
applied, so the original cannot be restored safely'}`, when the UI handles it, then: the server's own
`reason` is rendered **verbatim** beside that row; the row stays in the log; the corrections count
does not change; and the row is **not** marked Undone. A `catch {}`, a generic "could not undo", a
disappeared row, or a silently re-enabled button is a FAIL.
Given `{ok:false, reason:'no applied correction with seq 4'}` — the module's other refusal — the same
holds.
**A refusal is a real state the UI must render, not an error to swallow.**
**Where:** `unit` (the state mapper, both refusal strings) + `qc` (the reason text present in the DOM).

**AC-23 — success is decided by `ok`, never by the presence of `text`.**
Given `{ok:true, text:''}` — a correction reverted out of a field whose entire content was the
replacement — when the result is handled, then it is treated as a SUCCESS. An implementation
branching on `if (res.text)`, `res.text ? … : …`, or `!!result.text` is a FAIL, because the empty
string is falsy and the user would see a phantom refusal with no reason attached.
**Where:** `unit`.

**AC-24 — a reverted correction renders as "Undone" and does not disappear (P8.1 AC-11, `app/` half).**
Given a correction that has been reverted, when the log re-renders, then **two things hold
independently and are asserted separately**: the row is still present and marked Undone
(SPEC §5: "flips that row to 'Undone'"; P8.1 AC-11: "renders as 'Undone' rather than disappearing"),
and it is excluded from the "corrected" count while remaining in the list. A row that vanishes is a
FAIL; a row that stays but keeps counting as corrected is also a FAIL.
Corollary for AC-3: the count equals the number of **not-undone** rows, and the list length equals
all rows — the AC-3 identity is stated over the same population the count names, and the surface
must say which it is showing.
**Where:** `unit` + `qc`.

**AC-25 — after a revert, the log re-reads the payload rather than patching itself.**
Given a successful revert, when the surface updates, then it refreshes through the same single
payload the counters read (the `setResult` path in `useQcEntries`, QcRail.jsx:93) rather than
splicing the row out of component-local state — so the count, the gate and the log cannot diverge
from the server. A local `setState` that removes or mutates a corrections row is a FAIL.
**Where:** `unit` (grep: no local mutation of the corrections array in either `.jsx`).

**AC-26 — "suggest something different" is scoped, and obeys AC-20.**
Given the per-correction "suggest something different" affordance the backlog names, when it opens,
then it is labelled with the merge field it is scoped to and states that the scope is that field only
(SPEC §4.7: `ASK FOR A CHANGE · RESUME SUMMARY` … "Scoped to this field only."), and it is **either**
wired to a real submit path **or** not rendered — AC-20 applies to it identically.
**Where:** `unit` + `qc`.

**AC-27 — R6, per-field "ask for a change", same rule.**
Given P8.6's first bullet, when a field block renders, then the per-field "ask for a change"
affordance is present and scoped to that merge field, reachable **without going through the QC step**
(the backlog's own acceptance sentence), and it obeys AC-20: wired, or absent. Given `Show original`
(P8.6's second bullet), it renders the field's actual stored earlier text from the payload — for a

where the payload carries no earlier text it says so rather than showing the current text twice.
**Where:** `unit` + `blocks` (the asset-blocks probe is the field-block harness).

## 6. The two ACs most likely to fail on a first implementation, and why

### 6.1 AC-4 / AC-5 — absent vs empty. The mechanism is one house helper, and it is reached for reflexively.

`assetGate.js:247` is `export const arr = (v) => (Array.isArray(v) ? v : [])`. It is imported by
`qcRail.js`, by `QcRail.jsx`, by `AssetGateDrawer.jsx` and by `assetBlocks.js`, and it is the first
thing every function in those files does to any list it is handed — `arr(insertions && insertions.insertions)`,
`arr(swaps && swaps.swaps)`, `arr(row && row.offenders)`, `arr(entries)`. It is the correct helper
for all of those, because for an offender list "absent" and "empty" genuinely mean the same thing.

They do not mean the same thing here, and this is the one place in the file where they do not.

The implementer writes `const rows = arr(result.corrections)` because that is what every neighbouring
line looks like, and in that instant `undefined` and `[]` become the same value and the distinction
is gone before any of their code runs. Everything downstream is then correct: `rows.length` is 0,
the log renders its empty state, the count reads 0, every test they write passes, the screen looks
finished.

And it is wrong in the only state that exists today. Per M2, `checks-result` has no `corrections`
key on `main` **or** on the unmerged API branch — `git grep` finds three hits in `api/src` and all
three are comments. So **every artifact, for every user, until the API lane merges** will render
"nothing needed correcting" about a server that was never asked and never answered. That is a UI
telling the user its own text has been audited and found clean when no audit ran: P8.1's AC-14
vacuous green, moved from the check engine to the screen, and `CLAUDE.md`'s "A 200 with a zero count
is a result to investigate, not a pass."

The tell is not a red test — the tests pass. The tell is that the screen says the same words on the
day the API merges and the day before it, and nobody can tell those two days apart from the UI.

That is why AC-5 is written as a constraint on **where in the function the decision happens** rather
than on the returned value: a test on the return value alone can be satisfied by an implementation
that reads `result.corrections === undefined` in one branch and still calls `arr()` two lines later
for the list, which works until someone refactors the branch order. The decision must be made from
the raw key, first.

### 6.2 AC-12 — one definition, every surface. The number is a plain array length, and the guard that should stop it has a measured hole.

Every other number on these screens is expensive to compute — `railCounts` partitions by engine and
filters by state, `attentionSplit` does it twice, `coverageCards` walks requirements. Their cost is
what keeps them in a module. The corrections number costs nothing: it is `rows.length`. There is no
friction pushing it into `qcRail.js`, and the path of least resistance is to write it inline in the
JSX where the pill renders.

The structural guard that exists to prevent exactly this does not catch it. Measured (M5),
`qcRail.test.mjs:528` runs four negative regexes against `QcRail.jsx`:
`/\.filter\([^)]*\)\.length\s*\+\s*/` (needs a trailing `+`), the `fail || warn` state test, the
`.filter(r => r.engine` partition test, and `/gateFor|attentionCount/`. **`arr(result.corrections).length`
matches none of them.** The guard whose comment reads "a count bug shipped from a .jsx that did its
own arithmetic" is open in precisely the shape of the next count being added.

Then the two-module split does the rest. `assetGate.js` owns the badge's numbers; `qcRail.js` owns
the rail's and re-exports the assetGate selectors. An implementer working on the QC rail adds the
corrections number in `qcRail.js` or inline in `QcRail.jsx`, ships it, and it is right — on the QC
rail. `GateBadge` lives in `AssetGateDrawer.jsx` and reads `attentionSplit()` from `assetGate.js`;
it is rendered by `Library.jsx`, `OppDetail.jsx` and `PacketBuilder.jsx` as well as the drawer. So
the number is right on one surface and absent, or later reimplemented differently, on four.

This is the recurrence `CLAUDE.md` names twice: "fixing `FRESH_STAGES` in one `useMemo` but missing
`InboxScrubHero`… the KPI shows 51 but the hero still shows 216," and AssetGateDrawer.jsx's own
header comment recording that the badge once read `.counted` and printed "4 to fix" beside a gate
that could only fail on one. A badge and a gate disagreeing has shipped here twice. The corrections
count is the third opportunity, and it is the cheapest one yet to get wrong.

AC-12 is therefore written as a repo-wide grep — *no `.jsx` in `app/src/` may touch `.corrections`
at all* — rather than as "the number agrees on both screens." Agreement can be true by coincidence
on the day it is tested. The grep is true or false about the code.

## 7. What this lane CANNOT prove, stated plainly rather than papered over

**P8.1 AC-24 ("nothing behavioural is hardcoded") is NOT satisfiable in `app/` alone, and P8.6 must
not claim it.**

AC-24 requires auto-correct on/off and the generalisation vocabulary to be owner-changeable through
the existing settings path — it names `CheckThresholds`/`DEFAULT_THRESHOLDS` (`api/src/.../checks.ts`)
or `owner_search_prefs` (`api/src/.../remediation.ts`). Both are **persisted, per-owner, server-side**
stores. `app/` has no equivalent: `localStorage` is per-device and per-browser, which is not a user
setting, it is a cache — and `CLAUDE.md`'s rule is explicitly about a value "a user would reasonably
want to control" being exposed as a **user-changeable setting (Settings UI / config store)** that the
product owns.

So:

- **What this lane CAN prove:** that the change-log UI hardcodes no behavioural value of its own —
  AC-37. That is real and worth having, and it is a different claim.
- **What this lane CANNOT prove, and must not claim:** that auto-correct on/off is user-changeable.
  Rendering a toggle in `app/` before a route exists to persist it would be **dead UI** (AC-20) and a
  fake setting, which is worse than no setting: the user changes it, it survives until they clear
  their browser, and they believe the product is configured when it is not.
- **The correct outcome for this lane:** no auto-correct toggle ships in P8.6. **P8.1 AC-24 is
  recorded as NOT satisfied**, to be closed by the API lane when the prefs route lands, at which
  point the `app/` control is a small follow-up that AC-20 will already permit.

Three further items are API-side and are called out so nobody reads a green P8.6 as covering them:

1. **The re-opened check.** P8.1 AC-11's first half — reverting restores `$18M` and
   `posting_figure_echo` returns to `warn` with `$18M` in `offenders` — is `runChecks` behaviour.
   `app/` can prove the row renders as Undone (AC-24) and that the refusal renders (AC-22). It cannot
   prove the gate moved.
2. **P8.6's third bullet, keyword-level controls.** "Drop it and leave the posting line open …
   recording the coverage consequence" is a write that lowers a stored coverage number. There is no
   route. Under AC-20 the control must not ship in this lane.
3. **Any end-to-end claim at all.** Per §3, `ui-verify.yml`, `api-test.yml` and `db-query.yml` are
   all unavailable to this feature. Nothing here may be reported as verified against the live site
   or the live database, and per `CLAUDE.md`'s "Verify before reporting", the honest sentence when
   asked is "I cannot confirm this yet" plus what would confirm it.
