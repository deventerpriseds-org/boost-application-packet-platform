3. Gate sequence — what happens when an asset is generated

Today: generate → status review → a human approves. Target: generate → deterministic rules → blind reviewer → aggregate → gate. The gate state is what the badge shows and what the rail step enforces.

step 1

Generate draft

Unchanged. Produces artifact content plus skill_candidate and insertion rows instead of only text.

step 2 · deterministic

Rules engine

No model. Char limits (Q2, Q3), list counts (Q6), omit-list membership (Q1), AI-tell vocabulary and em-dash scan (Q7), word-count contracts (Q13), markup residue (Q8, Q9), empty template fields (Q14), whitespace (Q11). Emits check_result rows with offenders.

step 3 · independent

Blind reviewer

Separate prompt, separate call, does not receive the generator's rationale. Gets: posting text, requirement rows, the finished asset. Returns a grade, per-swap agreement, and citations that must resolve to a requirement_id.

step 4

Aggregate

Any fail ⇒ gate fail. No fails but any warn or reviewer disagreement ⇒ gate warn. Otherwise pass. Uncited swaps are always a fail, not a warn.

step 5

Score

Compute match_score against the requirement set. Stored per generation so regenerations are comparable.

step 6

Gate the approval

Approve stays disabled on a fail; a warn requires an explicit "approve with exceptions" that records who and why.

Decision for you. Should a warn block approval too, or only a fail? I've assumed fail blocks, warn requires an explicit override that gets recorded.

4. Match score

Three dimensions, as chosen. Weighted so a missing must-have cannot be papered over with keyword stuffing.

DimensionWeightDefinitionExpands to
Must-have requirement coverage50%Σ(weight of covered must_have) ÷ Σ(weight of all must_have). Covered = at least one insertion or existing passage the reviewer maps to that requirement.Requirement list, each row green/red with the passage that covers it
Keyword / ATS term coverage30%Covered ats_term ÷ all ats_term where source = posting_explicit. Terms only inferred by the model are excluded from the denominator and shown separately.Term chips, each linking to the posting line and the insert location
Seniority & scope alignment20%Reviewer-graded against posting signals (title band, team size, budget/P&L language, reporting line) versus what the asset evidences.Four signal rows with the posting quote and the asset quote side by side

composite = 0.5·must_have + 0.3·keyword + 0.2·seniority, banded ≥85 strong · 70–84 acceptable · <70 needs work. Both the composite and the three parts are stored — the number in the header is clickable down to the requirement that moved it.

Decision for you. Weights 50/30/20 and the banding thresholds. Also: score the ATS-compact resume separately from the full resume (they carry different skill blocks), which I've assumed yes.

5d. Intake — collecting the inputs up front

You left the intake scope open, so this is my call: the 13 hardcoded baseline values become a reusable profile edited in Settings, and the packet's JD step gains a short per-run block for what genuinely varies. Nothing per-run gets re-typed if the profile already has it.
