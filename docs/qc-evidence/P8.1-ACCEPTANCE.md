# P8.1 — Auto-correct before reporting (R1). Acceptance criteria.

**Status: acceptance criteria only. No implementation. Written by a cold reader who did not plan the work.**

Everything below is derived from the sources named in §1, plus four measurements taken in this
container (§2). Where I could not ground-truth something I say so and label it an inference.

## 1. What the sources actually say

### `docs/qc-evidence/BACKLOG.md` §P8.1 (lines 363-374), quoted verbatim

> ### P8.1 Auto-correct before reporting (R1)
> - [ ] Anything the rules engine can fix deterministically is fixed in the generated text before the
>       user sees it, and written to a `correction` row: `artifact_id`, `section_id`, `phrase`,
>       `replacement`, `reason`, `source` (`profile_figure` | `generalized`), `reverted_by`,
>       `reverted_at`.
> - [ ] The UI presents corrections as a change log in finished framing, with per-correction Undo and
>       "suggest something different". Reverting restores the original string in place.
> - [ ] Corrections never count toward the fix/review counters; they have their own count.
>
> **Acceptance:** a packet whose only problems are auto-correctable reaches the user with zero open
> items and a non-empty change log; undoing a correction restores the exact original substring and
> re-opens the corresponding check.

### `docs/qc-evidence/BACKLOG.md` §P8.2 (lines 376-390), the work P8.1 must give a home to

> - [ ] Replace with the candidate's own figure from the profile when one exists (`60+` → `62`,
>       `sixty engineers` → `sixty-two engineers`), otherwise generalize (`$18M` → `8-figure`,
>       `three business units` → `multiple business units`).
> - [ ] Applies to swap results too — a list item may not read `Org Scaling 60+` or `P&L $18M`.
>
> **Acceptance:** no generated field or list item contains a numeric string that also appears in
> `jd_real`; each replacement is logged with its reason; the check is deterministic and costs no
> tokens.

### `docs/qc-evidence/SPEC.md` §2, R1 and R3

> **R1 — Correct, then report.** Anything the system can fix, it fixes before the user sees it, and
> records the fix. The user reviews a change log, not a to-do list. Framing is finished
> ("Corrected", "Changes made"), never pending ("needs fixing"). Only what genuinely cannot be
> settled without the user appears as an open item.

> **R3 — … They are rewritten automatically — with the candidate's own figure from the profile
> where one exists, otherwise generalized — and each rewrite is logged and revertible.**

And SPEC.md line 334, in "Derivations that must not be duplicated in two places":

> - Figure rewrites (R3) are applied to the rendered text; reverting one restores the ad's figure in
>   place and flips that row to "Undone".

Note what that last line commits P8.1 to: the revert restores **the ad's figure**, i.e. the
document goes back to being wrong on purpose, at the user's instruction, and the R3 check must
therefore go back to naming it. A revert that silently keeps the check green is not a revert.

### `.claude/DEFERRED.md` — D1, D2, D3

D1: "The rewrite half of R3 does not exist… Only the *scan* is built."
D2: "`generalize()` has zero production callers. Tested dead code."
D3: "**Nothing computes the candidate's substitute figure.** `scanEcho` keys the profile side on the
*exact* figure… `shared[].profileRaw` looks like the substitute. It is the opposite: the figure that
must NOT be replaced." Trigger: "Before D1 — needs a design decision, and a resolver that guesses is
worse than generalizing."

**M2 — D3 is structural, and provable from three lines. Confirmed.**
`figureEcho.ts:338` builds the profile index as `new Map(profile.map(f => [f.key, f]))`.
`figureEcho.ts:349` looks up `profileByKey.get(figure.key)` — the *generated* figure's own key.

## 3. THE central question: extend `swap_decision` / `insertion`, or a new `correction` table?

**Observation.** I read both schemas — `main` at `api/src/functions/tests/schema.ts` and
`origin/claude/qc-p3-remediation` (`git show`) — and grepped both for `revert`, `undo`, and
`correction`. **Zero hits in either.** Nothing in this codebase today records "here is how to undo
it." The nearest thing is `artifact_gate.override_by/at/reason` (schema.ts:448-452), which records a
human *waiving* a finding, not a text change.

The two candidates, and what each actually records:

| | `swap_decision` (schema.ts:387-407) | `insertion` (schema.ts:416-434) |
|---|---|---|
| grain | one **list item**: `(packet_id, list, seq[, loop])` | one **whole merge field**: `unique (artifact_id, merge_field, loop)` (schema.ts:431) |
| the change | `from_label` → `to_label` | `before_text` → `after_text` |
| the why | `driver` + `rationale` + `verbatim_quote` | `requirement_id` + `verbatim_quote` (no free-text reason) |
| the undo | **nothing** | **nothing** |

**Measured (M4), against the live local cluster seeded with `main`'s schema:**

```
insert into swap_decision (packet_id, list, seq, action, driver)
values (…, 'ResumeSummary', 1, 'corrected', 'rule');
ERROR:  new row for relation "swap_decision" violates check constraint "swap_decision_action_check"

… same row with action 'swapped':
ERROR:  new row for relation "swap_decision" violates check constraint "swap_decision_list_check"
```

`swap_decision.list` is CHECK-constrained (schema.ts:390) to the five list names, and `action`
(schema.ts:392) to `kept|swapped|merged|dropped|added`. A correction to `$18M` inside the prose
`ResumeSummary`, `AboutMe1`, or the cover-letter body **cannot be stored there** without widening
two CHECKs and inventing a `seq` for a thing that has no ordinal.

`insertion` fails for a different reason: `unique (artifact_id, merge_field, loop)` makes it
structurally **one row per field per pass**. A single `ResumeSummary` can carry three echoed figures
and therefore three independently-undoable corrections. Widening that unique also breaks live
consumers on the P3 branch: `remediation.ts:248 realEdits()` and `remediation.ts:283
creditClosures()` read this table per pass and derive `edited_fields`, which the
`remediation_loop` CHECK `cardinality(closed) = 0 or cardinality(edited_fields) > 0` depends on.
Multiple rows per field would inflate `edited_fields` and make a phantom close creditable.

**Interpretation — my determination, stated plainly, as asked:**

> **This is a genuinely new grain, and a new `correction` table is the right answer — but the
> "extend, don't duplicate" rule is NOT thereby discharged. It binds P8.1 in three specific ways,
> which are AC-2, AC-3 and AC-17 below.**

The grain P8.1 needs is *a character span inside any merge field's value, individually revertible*.
Neither existing table can express it, and both would be damaged by being stretched to. That is the
"first state what exists, why it's insufficient" case the rule explicitly permits — not the
`taxonomy_title` failure the rule was written about, where a parallel system answered a question an
existing one already answered.

What the rule *does* still forbid, and what the ACs enforce:
- (a) `correction` must never become a second answer to "what is the current text of this field."
  `packet.pkg_json` stays the single source; `correction` stores only the delta needed to invert it.
- (b) A correction landing inside a list item must reconcile with `swap_decision.to_label`, or D5's
  divergence gets strictly worse — the rendered field is clean and the swap ledger still says
  `Org Scaling 60+`.
- (c) The correction COUNT must ride the existing `check_result` / `qcRail.js` pipeline, not a
  parallel counting path, or R4 ("one source per number") breaks the moment two screens disagree.

**Confidence: high, ground-truthed.** I read both schema files and executed the failing INSERTs.
The one thing I did *not* ground-truth: whether the owner would rather accept a widened
`swap_decision` and lose prose-field corrections entirely. That is a product decision, not a
technical one, and it is the only path by which this determination could be wrong.

## 4. The D3 decision the ACs require

**The ACs require GENERALIZATION. Substitution is out of scope for P8.1 unless it is built as the
exact-unit unique-match resolver specified in AC-10, and no implementation may write
`source='profile_figure'` without one.**

Reasoning, from M2: after `scanEcho` classifies a figure as `echo`, the result set contains no
profile-side candidate — not because a function is missing but because the profile index is keyed on
the number itself (`figureEcho.ts:338`). Answering "what is the candidate's corresponding number?"
means asking a *different* question — "how many engineers/sites/units does the profile say?" — which
is keyed on the **unit**, and `figureEcho.ts` builds a unit-keyed index for the posting only
(`postingClaims`, line 332), never for the profile.

Two honest ways forward, and one dishonest one:

- **Honest, in scope: generalize.** `generalize()` (figureEcho.ts:363) already exists, is tested
  (`figureEcho.test.mjs:145-155`), and returns `null` for a percentage because there is no honest
  generalisation of a rate. `null` means escalate, not rewrite. This is deterministic, costs no
  tokens, and satisfies the P8.2 acceptance sentence.
- **Honest, but must meet AC-10 if attempted: a unit-keyed profile resolver.** Substitute only when
  exactly one profile figure shares the *stemmed, exact* unit, with the profile record and offsets
  recorded as provenance. Zero matches or two-or-more matches must fall through to generalize.
- **Dishonest, and forbidden: anything that ranks.** Nearest-magnitude, most-recent-figure,
  best-fuzzy-unit-match. `CLAUDE.md` is unambiguous — "Fuzzy matching is for RANKING, never for
  ACCUSING" — and putting a guessed number into the candidate's resume is worse than accusing them:
  it is a fabrication they must defend in an interview. D3's own trigger says it: "a resolver that
  guesses is worse than generalizing."

So: **generalization is the only path P8.1 may ship by default.** `profile_figure` stays in the
`source` enum because the backlog names it, but writing it is an assertion about where a number came
from, and AC-10 makes that assertion unforgeable.

## 5. What must be stored for a revert to be possible

Answering the question directly before the AC that enforces it. A revert must be performable from
**the database row plus the current field text alone** — no in-memory context, no re-running the
scan, no model call, possibly months later and after the field has been rewritten by other passes.
That requires, at minimum:

1. `artifact_id` + the **real merge-field name** (the backlog says `section_id`; it must be a
   `TEMPLATE_META` merge field, per the precedent set at `insertions.ts:1-14` — "a row can never
   name a slot the document does not have").
2. `phrase` — the exact original substring, and `replacement` — exactly what was written.
3. `char_start` / `char_end` **into the pre-correction field string**, with
   `check (length(phrase) = char_end - char_start)` — the identical discipline
   `requirement_evidence` enforces at `schema.ts:362`.
4. `before_sha256` — a hash of the whole field value as it stood immediately before this correction
   applied. This is what makes a stale offset **detectable** rather than silently wrong, exactly as
   `requirement_evidence.record_sha256` (schema.ts:357) does for a profile record and
   `opportunity.jd_text_sha256` does for a posting. Without it, a later rewrite of the field shifts
   every offset and the revert writes the original phrase into the wrong place — which is worse than
   refusing.
5. `applied_seq` — the order corrections were applied within one field, so N corrections in one
   field can be reverted individually and in any order.
6. `reason` and `source` (backlog-named), so the change log can say *why* without recomputing.
7. `reverted_by` / `reverted_at` (backlog-named) — set on revert, **never a DELETE**. A revert that
   removes the row removes the change log entry that documents it.
8. `run_id` / `loop`, so a correction is attributable to the pass that made it.

D19 in `DEFERRED.md` is the standing warning here: `requirement_evidence.record_sha256` is *written
and served but never recomputed*, so stale offsets go undetected. P8.1 must not repeat that — AC-8
requires the hash be **verified on revert**, not merely stored.

## 6. Acceptance criteria

Format: `Given <context>, when <action>, then <observable outcome>.`
Each carries **Where**: `sandbox` (`cd api && npm test` / `npm run build`), `local-pg` (throwaway
PostgreSQL 16.13 cluster per M3), `api-test.yml`, `db-query.yml`, `ui-verify.yml`.

An AC is binary or it is not an AC. "Works correctly" appears nowhere below.

### A. The correction store and the extend-don't-duplicate constraint

**AC-1 — the table exists and is registered.**
Given a database created from `SCHEMA_SQL`, when the schema is executed, then a `correction` table
exists carrying at minimum `artifact_id`, `merge_field`, `phrase`, `replacement`, `char_start`,
`char_end`, `before_sha256`, `applied_seq`, `reason`, `source`, `run_id`, `loop`, `reverted_by`,
`reverted_at`, and `'correction'` appears in `EXPECTED_TABLES` (schema.ts:799) so a migration that
silently skipped it fails a test rather than 500ing at runtime (the D1/H11 precedent).
**Where:** `local-pg` (execute `SCHEMA_SQL` per M3, then
`select count(*) from information_schema.tables where table_name='correction'`); `sandbox` for the
`EXPECTED_TABLES` registration assertion.

**AC-2 — `correction` is not a second source of truth for field text.**
Given a corrected artifact, when the corrected value of any merge field is read from `correction`
rows alone and compared to `packet.pkg_json[merge_field]`, then the implementation contains no code
path that reconstructs field text from `correction` rows for display — `pkg_json` is read directly,
and `correction` supplies only the change log. A source grep asserting no consumer builds display
text from `correction` is acceptable here (a structural rule a runtime test cannot express, per the
H-case rules in `CLAUDE.md`).
**Where:** `sandbox`.

**AC-3 — a correction inside a list item reconciles with `swap_decision`.**
Given a `swap_decision` row whose `to_label` is `Org Scaling 60+` and a posting stating `60+`, when
the correction pass runs, then either (a) `swap_decision.to_label` is updated in the same
transaction as `pkg_json` and a `correction` row records it, or (b) the implementation documents in
the ACs' own terms that `to_label` is deliberately left stale and D5 is escalated — and in case (a),
`select to_label from swap_decision where …` shows no figure that `scanEcho` classifies as `echo`.
A third outcome — the rendered field corrected and `to_label` silently divergent with no record — is
a FAIL.
**Where:** `sandbox` for the unit-level reconciliation; `db-query.yml` post-merge to confirm no live
`swap_decision.to_label` still carries a corrected figure.

**AC-4 — one correction per span, idempotent across re-runs.**
Given an artifact already corrected at pass *n*, when the correction pass is re-run for the same
`(artifact_id, merge_field, run_id, applied_seq)`, then no duplicate row is created and the field
text is byte-identical to the first run's output.
**Where:** `local-pg` (unique constraint) + `sandbox` (pure-function determinism, mirroring
`figureEcho.test.mjs:170` which already asserts `scanEcho` is deterministic).

### B. Happy path — the backlog's own acceptance sentence

**AC-5 — an auto-correctable packet reaches the user with zero open items and a non-empty change log.**
Given an artifact whose only finding is `posting_figure_echo` naming figures that are all
generalizable, when the packet is built, then `attentionCount(results)` (checks.ts:620) returns 0 for
that artifact, `gateFor(results)` (checks.ts:602) returns `pass`, and at least one `correction` row
exists for the artifact.
**Where:** `sandbox` for `runChecks`/`gateFor`/`attentionCount` over a fixture; `api-test.yml`
(`POST /api/app/artifact/{id}/checks` or the packet build route) + `db-query.yml` for the live pair.

**AC-6 — the corrected text is what the user sees, and what the ledger records.**
Given a generated `ResumeSummary` containing `$18M` that the posting also states and the profile does
not, when the packet is persisted (`appPackets.ts:328`), then `packet.pkg_json.ResumeSummary`
contains `8-figure` and not `$18M`, and the `insertion` row written at `appPackets.ts:354` has
`after_text` byte-equal to that same corrected string.
**Where:** `sandbox` for the transform; `db-query.yml` for the live `pkg_json` / `insertion.after_text`
equality; `ui-verify.yml` with `expect: "8-figure"` for what actually renders.

**AC-7 — the corrections count is separate from the fix/review counters.**
Given an artifact with 3 corrections and 1 open `warn`, when the QC rail renders, then the badge
reads one to review and three corrected as **two distinct numbers**, `attentionCount` counts only the
warn, and both numbers derive from the same server payload (R4: one source per number).
**Where:** `sandbox` for `attentionCount` and the `qcRail.js` derivation; `ui-verify.yml` with
`expect` naming both strings.

### C. Revertibility

**AC-8 — a revert is possible from the stored row alone, and refuses when it is not.**
Given a `correction` row and the current `packet.pkg_json` value of its field, when a revert is
performed using **only** those two inputs, then the resulting field string is byte-identical to the
pre-correction string; and given the field has since been rewritten so that `before_sha256` no longer
matches, when a revert is attempted, then it **refuses with a stated reason** and writes nothing —
it does not write the phrase at a stale offset.
**Where:** `sandbox` (pure revert function over fixtures, both branches); `api-test.yml`
(`POST /api/app/correction/{id}/revert`) + `db-query.yml` for the live round-trip.

**AC-9 — a correction that cannot fund its own revert cannot be inserted.**
Given an attempted `correction` insert missing `phrase`, `char_start`, `char_end`, or
`before_sha256`, or where `length(phrase) <> char_end - char_start`, when the insert executes, then
the database **rejects it** — the constraint lives in the table (the `schema.ts:362` precedent), not
in a writer's good intentions. *This is the AC that fails if a correction is applied without enough
recorded to undo it.*
**Where:** `local-pg` — execute the schema per M3 and attempt each malformed insert; each must raise
a check-constraint violation. This is exactly the class of thing M3 makes newly checkable in the
sandbox, and the P3 branch's own comment ("Nothing in the sandbox can catch this — there is no
Postgres here") is now out of date.

**AC-10 — `source='profile_figure'` is unforgeable.**
Given any `correction` row with `source='profile_figure'`, when it is inspected, then it also carries
a `profile_source_key` and `profile_char_start`/`profile_char_end` identifying the stored profile
record the substitute number was read from, and the substring at those offsets equals the substituted
figure; and given a resolver returned zero or two-or-more profile figures sharing the echoed figure's
stemmed unit, when the correction is written, then `source` is `generalized` — never
`profile_figure`. A database CHECK enforces the column co-presence.
**Where:** `local-pg` (the CHECK); `sandbox` (the resolver's zero/one/many branching); `db-query.yml`
post-merge (`select count(*) from correction where source='profile_figure' and profile_source_key is
null` must return 0).

**AC-11 — reverting restores the ad's figure AND re-opens the check.**
Given a corrected `$18M` → `8-figure` and a green `posting_figure_echo`, when the correction is
reverted, then the field again reads `$18M`, `posting_figure_echo` returns to `warn` with `$18M`
named in `offenders`, and the change-log row renders as "Undone" rather than disappearing
(SPEC.md:334-335).
**Where:** `sandbox` (re-run `runChecks` on the reverted `pkg`); `api-test.yml` + `db-query.yml`
for the live gate transition; `ui-verify.yml` for the "Undone" row.

**AC-12 — a revert is append-only.**
Given a reverted correction, when the `correction` table is queried, then the row still exists with
`reverted_by` and `reverted_at` both non-null, and a CHECK enforces they are set together (the
`artifact_gate` override precedent at schema.ts:453 and `escalation`'s
`check ((resolved_at is null) = (resolved_by is null))`). A `delete from correction` on revert is a
FAIL.
**Where:** `local-pg` (CHECK + the row's continued existence); `db-query.yml` live.

**AC-13 — the actor is resolved server-side.**
Given a revert request carrying a client-supplied `reverted_by`, when it is processed, then the
stored `reverted_by` is the session-resolved owner email, not the client's value — the same rule
`artifact_gate` states in its own comment ("Actor is resolved SERVER-side from the session — a
client-supplied actor would make the audit row worthless").
**Where:** `sandbox` (handler unit test); `api-test.yml` (send a forged actor, then `db-query.yml`
to read what was stored).

### D. The vacuous-green trap

**AC-14 — "nothing needed correcting" and "the corrector never ran" are different observable states.**
Given artifact A with a readable posting and profile and no echoed figures, and artifact B whose
posting text is empty (or HTML-only, e.g. `<p></p>`), when both are checked, then A produces a
`corrections_applied` row with `state='pass'` and `observed` naming the fields actually scanned
(e.g. `0 corrections needed across 7 field(s)`), and B produces `state='not_applicable'` with the
scanner's own `reason` — and **neither is `pass` with an empty `observed`**. Both artifacts show
"0 corrections"; only one of them counts as having been checked.
**Where:** `sandbox` (two `runChecks` fixtures; assert `state` and `observed` differ). *This is the
AC that catches the vacuous green.*

**AC-15 — not_applicable propagates from the scanner, never re-derived.**
Given `postingText = '<p></p>'`, when the correction pass runs, then it asks `scanEcho` whether it
could look (`ScanResult.notApplicable`, figureEcho.ts:280) rather than testing the raw string itself
— the exact defect `checks.ts:273-282` documents and H27 already guards for the check. The
correction pass must be covered by the same invariant.
**Where:** `sandbox` (extend the H27-class assertion to the correction path).

**AC-16 — a swallowed exception is never a clean run.**
Given the correction pass throws (bad regex, missing profile record, DB error), when the packet
build completes, then `corrections_applied` is `not_applicable` with the error as its `reason` and
the gate does not read `pass` on the strength of a pass that did not happen. A `.catch(() => {})`
that lets the build continue silently — the shape at `appRemediation.ts:259` for insertion
provenance — is a FAIL here, because unlike provenance, a skipped correction changes what the user
reads.
**Where:** `sandbox` (inject a throwing dependency).

### E. Edge cases

**AC-17 — every consumer of `pkg_json` was traced, and named.**
Given the correction pass writes `pkg_json`, when the implementation is reviewed, then it names each
writer/reader of the same field and states how each reconciles: `appPackets.ts:328` (build persist),
`:334` `writeSwaps`, `:354` `writeInsertions`, `:686` and `:744` (the manual section-edit paths that
overwrite `pkg_json` and therefore invalidate every stored `char_start`/`before_sha256` for that
field), and `appChecks.ts:136` `runChecks`. A manual edit followed by a revert attempt must hit
AC-8's refusal branch, not a silent mis-write.
**Where:** `sandbox` (a test that edits a section then attempts a revert); the trace itself is a
review artifact, per the Stop-hook's integration/architecture-trace requirement.

**AC-18 — ordering: corrections apply before persistence, before checks, before insertions.**
Given a build at `appPackets.ts`, when the sequence runs, then corrections are applied to `pkg`
*before* the `update packet set pkg_json` at line 328, so that `writeSwaps` (334), `writeInsertions`
(354) and `runChecks` all see the corrected text, and `insertion.after_text` equals what the user
sees (AC-6). Corrections applied after line 328 are a FAIL even if the final rendered text is
identical, because the ledger would then disagree with the document.
**Where:** `sandbox` (assert call order / assert `after_text` equality); `db-query.yml` live
(`insertion.after_text` vs `packet.pkg_json` for the same field).

**AC-19 — multiple corrections in one field are independently revertible.**
Given `ResumeSummary` containing `$18M`, `60+` and `three business units`, all echoed, when the pass
runs, then three `correction` rows exist with distinct `applied_seq`, and reverting the middle one
restores only `60+` while the other two remain corrected.
**Where:** `sandbox` (offset arithmetic under partial revert — this is where offsets shift and where
`before_sha256` earns its place); `local-pg` for the unique on `(artifact_id, merge_field, applied_seq)`.

**AC-20 — a figure with no honest generalisation escalates, it does not get rewritten.**
Given an echoed `40%` (for which `generalize()` returns `null`, figureEcho.ts:373, asserted at
`figureEcho.test.mjs:151`), when the pass runs, then **no** `correction` row is written for it, the
figure stays in the text, and it remains named in `posting_figure_echo.offenders` as an open item for
the user. Silence is the correct output; a fabricated substitute is not.
**Where:** `sandbox`.

**AC-21 — a `shared_with_profile` figure is never corrected.**
Given a generated `60 sites`, a posting saying `60+ sites`, and a profile that also says `60 sites`
(the `shared` branch, figureEcho.ts:350), when the pass runs, then **no** correction is written and
the figure survives verbatim — R2 beats a literal reading of R3, as the scanner's own comment
(figureEcho.ts:290-293) already decided. Correcting a candidate's own true, evidenced number is the
most damaging failure available to this feature.
**Where:** `sandbox`. This case is already in `figureEcho.test.mjs:100`; the correction pass needs
its own assertion over the same fixture.

**AC-22 — replacement never breaks the field's own rules.**
Given a `SkillsBullets` item at 22 characters with a `relevantMaxChars` threshold of 24, when
`$18M` (4 chars) is replaced by `8-figure` (8 chars), then either the resulting item still satisfies
`runChecks`' length checks (checks.ts:200-211), or the correction is refused and the figure escalates
— a correction that silently pushes a field outside its own rule and reddens a different check is a
FAIL.
**Where:** `sandbox`.

**AC-23 — replacement is span-exact, not a global string replace.**
Given a field containing `60` twice, once as an echoed headcount and once inside an unrelated
`2019-60` range, when the correction applies, then only the span at `[char_start, char_end)` changes.
A `String.replace(phrase, replacement)` is a FAIL — and per `CLAUDE.md`'s "verify that an edit
applied" rule, a no-op replace must raise rather than report success.
**Where:** `sandbox`.

### F. Configuration and regression guard

**AC-24 — nothing behavioural is hardcoded.**
Given the correction feature, when its settings are inspected, then auto-correct on/off and the
generalisation vocabulary are owner-changeable through the existing settings path — extending
`CheckThresholds`/`DEFAULT_THRESHOLDS` (checks.ts:41-65, whose comment already states "Seeded first

**Where:** `sandbox` (threshold override respected); `api-test.yml` (`PATCH` the prefs route) +

**AC-25 — `generalize()` acquires a production caller, and the guard says so.**
Given `api/src/`, when `generalize` is grepped, then it has at least one non-test caller in the
correction pass (D2 closed), and D2 is struck from `.claude/DEFERRED.md` in the same commit — per

**Where:** `sandbox` (`grep -rn generalize api/src/` — currently returns only the definition at
figureEcho.ts:363, per M1).

**AC-26 — the regression guard is an H-case, not a note.**
Given P8.1 lands, when `api/test/hardening.test.mjs` is read, then it contains at least two new

**Where:** `sandbox`.

**AC-28 — the schema migration survives an EXISTING database, not just a fresh one.**
Given a cluster already seeded with `main`'s `SCHEMA_SQL` (i.e. production's shape), when P8.1's

two-cluster test (fresh vs seeded) that no unit test can express and that the sandbox was previously
believed unable to run.

## 7. The two ACs most likely to fail on a first implementation, and why

### 1. AC-18 (ordering) — and it will fail while looking like it passed.

`appPackets.ts:328` persists `pkg_json`; `:334` calls `writeSwaps`; `:354` calls `writeInsertions`.
The natural place to add a correction pass is *after* the pkg is complete and *near the check that
motivated it* — and the check runs later, in `appChecks.ts:136`. An implementer who applies
corrections just before `runChecks`, or in the checks path, gets a green `posting_figure_echo` and a
correct-looking change log, and every test they write will pass.

What actually breaks is invisible from that vantage point: `insertion.after_text`
(written at `appPackets.ts:354` from the *pre*-correction `pkg`) and `packet.pkg_json` (written at
`:328`, also pre-correction) now disagree with the document the user reads. That is precisely the
class `CLAUDE.md`'s "Trace every dependent" rule exists for — "stale/mismatched numbers almost
always mean a value was applied off the core funnel." And on the P3 branch it compounds:
`remediation.ts:248 realEdits()` decides a row is an edit by comparing `after_text` to `before_text`,
and `creditClosures()` (remediation.ts:283) joins `after_text` into `writtenText` to decide which
requirements a pass may take credit for. Corrections applied off-funnel mean the loop credits
closures against text that is not what shipped.

The tell that it went wrong is not a red test. It is `db-query.yml` returning a row where
`insertion.after_text <> packet.pkg_json->>merge_field` — which is why AC-18 names that query
explicitly.

### 2. AC-19 (independent revert of multiple corrections in one field) — the offsets are a trap with a specific shape.

`figureEcho.ts:158-264 extractFigures()` returns figures with `start`/`end` measured against **one**
input string, sorted ascending (`figureEcho.ts:263`). The obvious implementation walks that array and
applies each replacement in order — at which point every correction after the first has recorded
offsets that no longer index the string it lives in, because `$18M` (4 chars) became `8-figure`
(8 chars) and shifted everything right by four.

Two failure modes follow, and the first is the dangerous one:

- Apply left-to-right, record the *original* offsets: the change log is correct, but a revert of
  correction #2 writes `60+` at an index that now points into the middle of `8-figure`. AC-8's
  `before_sha256` check is the only thing standing between that and a corrupted field — and it only
  helps if the hash is **verified**, not merely stored. `DEFERRED.md` D19 is the same defect already
  shipped once: `requirement_evidence.record_sha256` "is written and served but never recomputed."
- Apply right-to-left to keep earlier offsets stable: correct on the way in, but now `applied_seq`
  is descending relative to `char_start` and any revert that replays "all corrections except this
  one" from the original text will reorder them.

There is a further wrinkle specific to this data. `extractFigures` can emit **overlapping-adjacent**
figures — the currency scanner claims `$18M`, then the range scanner and bare-count scanner skip
spans already claimed (`figureEcho.ts:199`, `:218`, `:256`) — so the array is non-overlapping *by
construction within one pass*, but nothing guarantees a correction's replacement text does not
itself contain a digit that the *next* scan will extract. `generalize()` returning `8-figure`
introduces the literal `8`. If the R3 check re-runs against the corrected text (which AC-11 requires
it to, in the revert direction), an implementation that does not exclude corrected spans can
re-flag `8-figure` as an echo of any posting mentioning eight of anything — a self-inflicted
cry-wolf, which is the exact failure `figureEcho.ts:54-60` was written to prevent.
