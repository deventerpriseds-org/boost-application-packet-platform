## 2. ACCEPTANCE CRITERIA

### Score — interim keyword_coverage (S-series)

**S1.** Given a `resume`-type artifact whose packet's most recent `last_build.analysis` contains a section titled `Missing ATS Skills` that parses into ≥1 HTML table row, when `evaluateArtifact` runs, then `keyword_coverage.value = round(covered / total * 100)` where `total` = parsed rows and `covered` = rows whose "covering skill / list location" column is not the literal `Missing` (trimmed, case-insensitive), and `keyword_coverage.source` names it as an interim, non-library source (e.g. `"7/9 ATS keywords covered (interim: resume draft's own ATS table, not the term library)"`).

**S2.** Given a `resume` artifact whose packet has NO `Missing ATS Skills` section (never built, or Call 1 produced no unmapped sections that round-trip), when `evaluateArtifact` runs, then `keyword_coverage = {value: null, source: "<reason>"}` — never `0`, and never silently filled from `packet.covered_kw` or `packet.ats_score` (both disqualified per the feasibility table above).

**S3.** Given a `Missing ATS Skills` body that exists but fails to parse as an HTML table (no `<table>` tag, zero extractable rows, or a row shape the parser doesn't recognize), when parsed, then `keyword_coverage` is `null` with a source string naming the parse failure — the whole `evaluateArtifact` call must not throw or abort because of this one component, matching the existing pattern where a bad `must_have_source` string yields `null` rather than a guess (`artifactScore.ts:79-84`).

**S4.** Given an artifact of type `cover`, `portfolio`, or `compact_resume`, when `evaluateArtifact` runs, then `keyword_coverage` stays `null` with source `"no per-artifact ATS keyword table exists for this artifact type yet"` — explicitly NOT backfilled from the sibling resume artifact's table, because a cover letter does not place the resume's skills lines and crediting it with the resume's coverage would be exactly the fabricated-component failure `artifactScore.ts`'s own header forbids.

**S5 — THE SUPPLEMENT RULE.** Given a term-library version WITH scoreable published entries exists for the owner, when `evaluateArtifact` runs, then `keyword_coverage` is sourced from the published library via the existing path (`appChecks.ts:209-218`) and the interim Call-1-table source (S1) is not consulted at all — library-published is a strict override, never blended or averaged with the interim number.

**S6.** Given a term-library version transitions from "no scoreable entries" to "published with scoreable entries" between two check-runs of the SAME unchanged artifact, when the second run's `artifact_score` row is written, then its `keyword_coverage.source` string changes from the interim wording (S1) to the library wording, and the prior run's row in `artifact_score` history is left untouched — so any screen rendering score-over-time can attribute a jump in the number to a *source change* by reading `source`, never leaving the owner to wonder whether their resume changed.

**S7.** Given the interim source (S1) is the one active for a rendered artifact, when the UI displays `keyword_coverage`, then it must render `keyword_coverage.source` alongside the number, not the number alone — per this repo's standing rule that a partial or differently-sourced composite is the number a reviewer trusts most and the most likely to be wrong. If UI work is out of scope for this pass, this AC must be explicitly deferred in writing (owner sign-off), not silently dropped.

**S8 — regression guard.** Given today's exact production state (zero scoreable term-library entries, and — for packets built before this change ships — no `Missing ATS Skills` capture yet parsed), when `evaluateArtifact` runs, then behavior is byte-identical to current production: `keyword_coverage = {value: null, source: 'no published term-library version has scoreable entries yet'}`. This full sentence, not just the null, is asserted by existing tests and must not change wording as a side effect of adding S1-S6.

### Reviewer — wiring (R-series)

**R1.** Given a new owner setting (e.g. `chk_reviewer_auto`, boolean, seeded default `false`, added to the same `CheckThresholds`/`chk_*` column family as `chk_coverage_judge` in `checkPrefs.ts`) is at its seeded default, when a packet build runs, then `runReview` is never called from the build path — every existing build behaves exactly as it does today (this is the answer to the brief's D3: the score does nothing different between now and an owner turning the setting on).

**R2.** Given the setting is ON for an owner, when the build loop at `appPackets.ts:1137-1145` completes an `evaluateArtifact(client, art.id, owner)` call for an artifact WITHOUT throwing, then `runReview(client, art.id, owner)` is called for that same artifact next, sequentially on the same connection (not `Promise.all`, for the identical begin/commit-nesting reason `evaluateArtifact` itself is already sequential there), inside its own non-fatal try/catch.

**R3.** Given `evaluateArtifact` for an artifact THREW (so no `artifact_gate` row exists for it), when the build loop proceeds, then `runReview` is NOT attempted for that artifact — `runReview` already refuses with `'run the deterministic checks first'` when no gate row exists (`appReviewer.ts`), so calling it anyway only produces a second, redundant failure describing the same root cause.

**R4.** Given the setting is ON and review runs (successfully or not), when the build's HTTP response is assembled, then it surfaces a reviewer summary in the same place `evaluateArtifact`'s own `judge` field already reports coverage-judge/stuffing spend (the F-8 fix in `appChecks.ts`) — at minimum `ran`, `grade`, `agreed`/`disagreed`, `citations_kept`/`citations_dropped` — so a reviewer outage is visible exactly where a coverage-judge outage already is, not a second silent failure mode.

**R5.** Given one artifact's review call fails (network, parse, model outage) during a four-artifact packet build, when the build completes, then the other three artifacts' own checks, scores, and (if reviewed) verdicts are unaffected — the existing `checkWarnings` isolation pattern is extended to reviewer warnings, never replaced by a build-wide try/catch.

**R6.** Given the setting is ON and a review completes successfully for an artifact, when `artifact_score` is read afterward for that artifact's run, then `seniority_alignment` reflects the reviewer's graded value via the existing `persist()` UPDATE path in `appReviewer.ts` (no new write path needed) — confirming that turning the setting on is sufficient by itself to make the third score component (weight 0.2) fillable.

**R7 — regression guard.** Given the setting does not yet exist in the schema (today), when a packet is built, then `artifact_score.seniority_alignment` stays `null` exactly as it does today, and nothing besides the existing manual `POST .../review` route can reach `runReview` — i.e., shipping the setting column alone (before wiring R2) must not change production behavior for any owner.

**R8.** Given the setting is added to the `checks` object already accepted by `searchPrefsSet`/`searchPrefsGet` (`app/src/api.js`), when an owner changes it via the existing Settings screen path, then it round-trips through `loadThresholds`/`resolveOptionsFrom` exactly as `chk_coverage_judge` does today — no second settings table, route, or screen is created for it.

### Closing D4 (must_haves)

**M1.** Given `packet.must_haves` is `NULL` (today's state on all 8 production packets), when `PacketBuilder.jsx`'s post-analysis strip renders `mustHaves: (a.mustHaves||[]).length`, then the implementer must pick ONE explicitly and record which: (a) leave it as-is because it only ever reads a fresh `analyzeJd` response body, never the stale stored column, and document that decision inline; or (b) distinguish "not yet analyzed" from "analyzed, zero must-haves" in the strip. Silently leaving the ambiguity unaddressed is not an acceptable outcome of this pass, even though the underlying UI nuance is low-traffic enough that deferral (option a) is a legitimate answer.

## 4. WHAT IS WRONG IN THE BRIEF

- **C1-C5's shared premise is false.** The brief assumes `covered_kw` + `Missing ATS Skills` form one coherent keyword-coverage measurement. They do not, and the codebase already says why: `jdAnalysis` (the writer of `covered_kw` and `packet.ats_score`) sees ONLY the posting text — `comparesToProfile()` is `false` on that path by construction (`appPackets.ts:1268-1273`, `:1242`) — and the file's own D14 comment explicitly rejected building a "fourth number named keyword coverage" from exactly this kind of ungrounded call, because it would have to agree with the three systems that DO measure against the candidate and could not. `Missing ATS Skills`, by contrast, genuinely does compare the candidate's own skills lists to posting keywords (verified in the zap prompt source, `docs/zap-289877647/prompts/16-...md:322-338`) but comes from a completely different pipeline (packet build's Call 1, not `jdAnalysis`), is resume-artifact-only, and reflects the PRE-swap draft rather than what Call 3's ATS-QC pass actually ships. The brief paired the wrong two numbers; §1's feasibility table and S1-S8 substitute the right one.
- **The brief's live DB read is mislabeled.** "`packet.ats_score` — 85" is quoted as if it were the posting-grounded, candidate-compared number `artifactScore.ts`'s own header comment describes ("opportunity.ats_score — posting-grounded, from atsScoreOne"). It is not — that is `opportunity.ats_score`, a different column on a different table, written by a different prompt (`appApply.ts:171-183`) that DOES embed the candidate's master-context baseline. `packet.ats_score` is written by the same ungrounded `jdAnalysis` call as `covered_kw`. Two same-named columns computing different things is itself worth a follow-up regardless of this brief's outcome (guard 8 above is the minimum containment).
- **The suite count is stated wrong.** The brief says "`cd api && npm test` (1022 passing)". Live run on this exact branch/commit: 993 pass, 3 fail, 26 skipped, of 1022 total. The 3 failures are in `deferredLedger.test.mjs` (`D:ledger-rows-parse`, `D:ledger-open-carries-check`, `D:ledger-manual-names-its-vehicle`) — a pre-existing DEFERRED.md formatting issue, unrelated to score/reviewer work, not something these ACs or their guards should be blamed for or expected to fix — but "1022 passing" must not be quoted as the current green baseline in a verification pass. `cd app && npm test` is confirmed accurate at 424/424.
- **D4 ("does anything read must_haves") is answered too absolutely.** There IS a reader: `PacketBuilder.jsx:572`. It is a narrow, ephemeral one (a live post-run count, never a persisted redisplay, nothing scores off it) — see M1 — but "nothing reads it" would have been wrong to assert outright.
