## §1 — D14 acceptance criteria

Form: `Given <context>, when <action>, then <observable outcome>.` Each carries the **single**
artefact that proves it true or false.

### Happy path — the claim is structural, not prose

**AC-D14-01.**
*Given* the label, the count noun and the provenance sentence for the `covered_kw` list are exported
from `app/src/postingAnalysis.js` as the return of a pure function (name it, e.g.
`keywordGroupProvenance(group)`), *when* `app/test/postingAnalysis.test.mjs` imports that module
with no React and no DOM, *then* the function returns, for the `from-run` group, a `source` of
`'posting_only'`, a `comparedToProfile` of `false`, and a `text` that contains no case-insensitive
match for `/\bcover(ed|age)\b/`.
→ **Artefact:** the passing/failing assertion in `app/test/postingAnalysis.test.mjs`.

**AC-D14-02.**
*Given* that function is the only source of those strings, *when* a test greps
`app/src/screens/PostingAnalysis.jsx` with comments stripped by the existing `stripComments` helper,
*then* no string literal in the JSX contains the rendered provenance sentence — the JSX reads it
from the module.
→ **Artefact:** the source-grep assertion in `app/test/postingAnalysis.test.mjs` (same shape as the
existing "the card hand-types none of them" test at line 354).

**AC-D14-03.**
*Given* the three keyword groups (`parsed`, `from-run`, `thin`), *when* the component renders any
one of them, *then* the group element carries a machine-readable provenance attribute
(e.g. `data-qc-compared="false"` on `parsed` and `from-run`, `"true"` on `thin`) in addition to the
existing `data-qc-group`, and the attribute value is taken from the module function, not written
inline.
→ **Artefact:** `ui-verify.yml` on `#/packet/<id>/jd` with an `EXPECT` selector
`[data-qc="keyword-group"][data-qc-group="from-run"][data-qc-compared="false"]`.

**AC-D14-04.**
*Given* a packet whose `covered_kw` is non-empty, *when* the JD step renders, *then* the `from-run`
chips carry no `--proto-green*` token in any inline style and no `tone` prop, and the only tinted
keyword group on the screen is `thin`.
→ **Artefact:** a Node test over the rendered probe (`app/test/browser/overlay-probe.jsx` already
mounts `ModelKeywords` with `coveredKw`) asserting the computed background of a `from-run` chip
equals the `parsed` chip's and differs from the `thin` chip's.

## §2 — D33 acceptance criteria

### Happy path — the authored file is provably the live prompt minus exactly four sections

→ **Artefact:** a `sha256` of the reconstruction compared to a `sha256` of the extracted

**AC-D33-02 (the one that decides whether AC-D33-01 is worth anything).**
*Given* G9 — the doc's `user_message` is 29,069 chars and `5c138a6` records live `resume_user` as

**AC-D33-03.**
*Given* the file is loaded via `prompts-load-file.yml` with `partitionKey=resume_user`, *when* the

→ **Artefact:** the `prompts-load-file.yml` job log (`HTTP 200 … {"saved":true,…,"version":N}`)

**AC-D33-04.**
*Given* the new prompt is active, *when* one packet is built end to end on the same opportunity used

→ **Artefact:** the `api-test.yml` build-all job log for that opportunity, showing the warnings

**AC-D33-05 (the claim D33 actually makes).**
*Given* the stated motive is "the model spends tokens producing content nobody reads", *when* the

→ **Artefact:** a `db-query.yml` run of
`select pass, prompt_tokens, completion_tokens, created_at from usage_metering where pass like '%resume%' order by created_at desc limit 4`.
An unquantified "saves tokens" does not satisfy this AC. This measurement is known to be feasible on
exactly this path: `693e929` closed D31 by observing Call 2's input fall from ~16,000 tokens to
5,118 after the correct portfolio prompt was loaded.

## §3 — Adversarial reading of the D14 decision

### A. The relabel is already shipped. The lane risks reporting prose as work.

G1/G2: on `main`, the chips are already untoned and the copy already says "it is not a coverage
list". If the implementer writes a before/after in which the before-state is green "N covered"
chips, **that before-state does not exist** and the commit will be a false claim about the
starting point. What is genuinely missing is only the enforcement — AC-D14-01, -02, -11, -12.
Scope the commit to that and say so.

### B. What a different owner would prefer, and why they would be right

The spec and the prototype define this field as **coverage**: `docs/design_handoff/proto/state.jsx:57`
— `coveredKw: [], // keywords currently worked into the resume` — and the prototype's own copy reads
"Fill the N gaps to top out" (`proto/packet.jsx:269`). The affordance was designed around a
candidate comparison. Relabelling keeps the column, keeps the model call, and delivers a list the
owner cannot act on: a set of role keywords with no statement about their own profile. An owner
looking at the product rather than at the honesty of the label will ask why the screen now costs a
model call to print something explicitly marked as meaning nothing.

The stronger objection is the repo's own **"Extend, don't duplicate"** rule. A candidate comparison
already exists three times over — `appApply.atsScoreOne` (candidate master baseline vs posting),
`must_have_coverage` in `checks.ts`, and the P8.4 dimension comparison. Option (a) is not "write a
new comparator"; it is "point this list at one that already runs". Choosing (b) without saying which
of those three was considered and rejected is the shape that rule exists to prevent.

**There is also an option (c) nobody has costed: delete it.** G3 says `covered_kw` has two readers
and both are the UI. If the honest label is "a list we cannot interpret", the cheapest correct move
is to stop generating it and delete the column, saving the tokens outright. A relabel that keeps an
uninterpretable list on screen is the most expensive of the three options and the least decisive.
At minimum the commit must say why the list is still worth rendering.

### C. Concrete things the implementer is likely to get wrong

1. **Testing the sentence instead of the invariant.** A test asserting the exact string "Read from
   the posting only…" is a spelling test: rewording the copy breaks it, and re-tinting the chips
   does not. See §5.
2. **Guarding the JSX and not the data.** The lie is that a model call with no candidate input
   yields a candidate property. Only AC-D14-12 encodes that; the rest encode today's markup.
3. **Leaving the neighbours lying.** G4: the *thin* count is silently capped at 12, so
   "Compared against your profile and flagged as thin - N model-suggested" understates by an unknown
   amount whenever the model returns more than 12. G5: `atsScore` on the packet screen comes from
   the same candidate-blind call as `covered_kw`, and the big number in `MatchEstimateButton` and the
   tally overlay is that one. Fixing the chips and leaving a candidate-blind percentage rendered at
   30px in green/red above them relocates the defect rather than closing it. (`PostingAnalysis.jsx:550`
   and `:579` do carry hedging prose — which is exactly the unenforced-prose pattern this lane is
   supposed to be ending.)
4. **The ungrounded case.** AC-D14-08: when `jd_grounded` is false the model never saw a posting, so
   even "pulled out of the posting" is false. `jd_grounded` is written on the packet but is **not**
   in `packetShape`, so the UI cannot currently tell. Expect this to be missed, and expect the miss
   to be invisible because the grounded case is the common one.
5. **Claiming it live from a green suite.** The proving artefact for anything rendered is
   `ui-verify.yml`, not `npm test`. Per the D25 pattern, "verified" here will mean the mechanism,
   not the product, unless a run id is in the commit.

### D. What will be claimed without proof

- "The list is no longer described as coverage." — provable only by AC-D14-11's three reinstatements.
- "No other screen makes the same claim." — requires the `grep` in AC-D14-13, over both `app/src`
  and `api/src`, per the fix-all-consumers rule.
- "Verified live." — requires a `ui-verify.yml` run id and the `UI_VERIFY_RESULT` line.

## §4 — Adversarial reading of the D33 decision

### A. The unmeasured risk: those sections are the model's reasoning, not its waste

`Missing ATS Skills` and `Missing ATS Swap Suggestions` are not decorative appendices. They are the
step where the model cross-checks the skills it already emitted against the JD's ATS keywords and
proposes swaps, and the skills-generation block earlier in the same prompt is written to interlock
with them ("Step 2: Review & Update for Missing Items"). `Second Job Description Check` is what
produces the "Missing" tagging those sections consume. Deleting the tail of a chain-of-thought and
keeping the head is a **generation-quality change**, not a cleanup — and the sections whose quality
it changes (`Skills1`, `Skills2`, `Relevant 1-3`, `Expertise`) are precisely the ones that ship.

Note the asymmetry that makes this cheap to get wrong: the removed sections' *output* was discarded,
so removing them looks free. But the model produced them **after** the mapped sections and the
prompt tells it to feed the result back ("Provide an updated ### Skills1 ###…"). The parser then
throws the updated lists away because first-occurrence-wins (`resumeParser.ts:151`). So the swap
work was *already* dead — which is an argument for removal — but it is an argument nobody in this
lane has verified end to end, and the only honest way to settle it is AC-D33-10's before/after check
comparison, not reasoning. **Predict this will be skipped.**

### B. What a different owner would prefer

The D33 row states the choice as the owner's: "drop them from the prompt, **or** give them a field".
Two of the four are the most owner-visible content in the run. `Jobscan Extraction` (2,888 output
chars) is a per-skill JD-source-phrase → resume-destination-phrase table — that is *evidence
provenance*, which is the thing three other lanes (P8.1 corrections, P8.3 evidence, P8.4 dimensions)
built whole subsystems to obtain. `Missing ATS Skills` (940) is the gap list the JD step renders from
a *separate, capped-at-12, differently-timed* model call (G4). An owner could reasonably say: you
are about to delete the one artefact that ties each resume skill back to the JD phrase that
justified it, in a product whose entire QC thesis is provenance. Dropping it is defensible only if
someone says out loud that the R3/P8.3 machinery supersedes it — and the commit should say that.

There is also a **status** objection: this is the owner's decision, not the implementing agent's.
D33's trigger column reads "Owner decides". The lane should record the go-ahead or explicitly mark
the choice as provisional and reversible (the prompt is versioned in the table — `version+1` and a
`notes` string — so reverting is one dispatch; say so).

### C. The factual defect in the plan

**The four-section list is derived from an incomplete detector.** G6 proves `_unmapped` cannot see
`Job Description Summary` at all — the unanchored `summary` regex claims it for `resumeSummary`,
which is already filled, so `keys.find(k => !fields[k])` returns `undefined` and the section
evaporates with no warning. G7 adds `Second Job Description Check`, which `_unmapped` *does* see and
which D33 nonetheless omits. G8: those two are 3,353 prompt chars against the 2,743 being removed.
**The cleanup removes less dead prompt than it leaves behind, and the row it is working from does
not know that.** Any commit that says "the dead sections are gone" without addressing these two is
wrong on the facts.

This also means `resumeParser.ts`'s comment — "the overlap itself is a latent defect … Left as-is
deliberately — the live prompts emit Skills first" — is understating it. The overlap is not latent;
it is firing today, on the largest section in the prompt.

### D. The provenance risk on the file itself

G9: the doc is one character and a different digest away from what is live. G13: the sibling file
`prompts/portfolio_user.txt` has *already* drifted from its doc. The brief calls the doc "the primary
source for the live `resume_user` prompt" — that is an inference, and the repo's own
ground-truth-before-answering rule says the primary source here is **the live table row**, read via
`GET /api/prompts`. Authoring from the doc and loading it overwrites whatever the live row actually
contains, including any hand-edit made in the dev console's Prompts screen, **silently**, because
the POST simply deactivates the old row and writes `v(N+1)`. AC-D33-02 exists for exactly this. It
is the AC most likely to be skipped, because the doc is right there and reading the live row costs a
workflow dispatch.

### E. Other concrete things likely to go wrong

1. **"14 structured sections" left in place** (G10). Left uncorrected, the model has an explicit
   instruction to produce more sections than the prompt now defines, and the most likely way it
   satisfies that is to invent headings — which land in `_unmapped` and recreate the exact warning
   this work exists to clear.
2. **Dangling forward references** (G12) — the soft-skill "recalled later" promise and the "provide
   an updated Skills1…" instruction.
3. **Removing the section header but leaving its trailing block.** The `(Don't output this as a
   header - Skills Lists) … return "Moved" for both lists` block sits *between*
   `Missing ATS Swap Suggestions` and `Word and Character Requirements Check`. A naïve
   heading-to-next-heading delete takes it with the swap section; a line-range delete may leave it
   orphaned. Either is defensible, neither is safe unattended — decide and state which.
4. **Loading without reading back.** A 200 from the dispatch is not a version bump. AC-D33-03.
5. **Not measuring the token saving** (AC-D33-05) while asserting it, which is the exact
   "verify before reporting" failure the repo has hardened against twice.
6. **The `_unmapped` warning going quiet being read as success.** After the removal the warning list
   *will* be shorter. That is consistent both with the fix working and with the model having stopped
   emitting bookended headings for some other reason. The distinguishing artefact is the built
   document's field contents, not the absence of a warning — a 200 with a zero count is a result to
   investigate.

## §5 — Guards that would be INERT, or that test spelling rather than behaviour

Written in the shape the repo's own D3 post-mortem uses: the tempting version, why it does nothing,
and the version that has teeth.

| Tempting guard | Why it is inert / spelling-only | The behavioural version |
|---|---|---|
| `assert.ok(!/covered/i.test(POSTING_ANALYSIS_SRC))` — grep the JSX for the word. | Tests **spelling**, and cries wolf immediately: the file legitimately contains `coveredKw`, `covered_kw` and the word "coverage" in the term-library card at `:587`. It will be weakened to a narrower regex within a day, and then it guards nothing. | Assert on the **rendered output of the pure function** for the `from-run` group (AC-D14-01), and on the **absence of a tone token** on that group's chips (AC-D14-04). Words are free to change; the provenance value and the tint are not. |
| `assert.match(src, /it is not a coverage list/)` — pin the sentence. | Pure spelling. Passes with the sentence present and the chips green. Breaks on a harmless rewording. | Pin the *property*: `keywordGroupProvenance('from-run').comparedToProfile === false`, and pin that the component reads it (AC-D14-02). |
| `assert.ok(!/Missing ATS Skills/.test(promptFile))` — grep the prompt for the four titles. | Tests **spelling of four literals**. Renaming a section to `Missing ATS Keywords` passes it while reintroducing the defect; adding a fifth dead section passes it too; and it says nothing about `Job Description Summary`, which is the biggest offender (G6). | AC-D33-13: extract **every** heading the prompt instructs the model to emit, run each through the real `headingKeysFor`, fail on any that maps to no field *or* only to an already-claimed field. Invariant, not incident. |
| `assert.equal(promptFile.length, 26327)` — pin the char count. | Inert as a *behavioural* guard: it detects any edit, including correct ones, so it becomes a number someone updates reflexively. It is a change-detector, not an invariant. | Keep a length/digest **assertion against the live row** as an AC-D33-02 evidence step, not as a standing test. The standing test is AC-D33-13. |
| A test asserting `_unmapped` is empty for a hand-written fixture the implementer also authored. | Vacuously true: the fixture is written to contain only mappable headings. It proves the fixture, not the parser or the prompt. | AC-D33-14: **two** fixtures, one for the unmapped case and one for the duplicate-title silent-drop case, each proved by reinstating the defect and watching the named assertion fail. |
| Asserting the pipeline emits zero `"maps to no merge field"` warnings, in a unit test with a stubbed model reply. | The stub is the implementer's own text, so it is the fixture problem again, and the real risk (what a live model emits under the edited prompt) is untouched. | AC-D33-04: the warnings array from a **real build-all run** on a real opportunity, read from the `api-test.yml` job log. |
| `H:…` case that greps `appPackets.ts` for the string `ATS keywords for this role` to prove the prompt is candidate-blind. | Spelling. Rewording the system prompt to `keywords an ATS would extract` passes it while the call is just as candidate-blind. | Assert the **shape of the request**: that the `user` message built by `jdAnalysis` contains no MasterContext/profile substring, by executing the message-construction with a sentinel profile value and asserting the sentinel is absent. That is the property "no candidate input", and it survives rewording. |
| Any test that asserts a `data-qc` attribute exists in the JSX **source**. | The existing hook tests already do this and are correct as *source* tests, but they cannot prove the attribute renders — a conditional above it can make it unreachable. | Pair the source test with a `ui-verify.yml` `EXPECT` on the selector (AC-D14-03). The repo already treats this as the standard: the breakpoint is rendered as `data-qc-cols` precisely so a live run can select it. |

**One further inertness trap specific to this pair of items.** `H26` fails the suite on any new
numeric H-id, so both guards must take two-word slugs (`H:covered-kw-is-not-coverage`,
`H:prompt-sections-are-mappable`). And per the hardening rule, each must be committed **with** the
fix and **with** the reinstatement evidence in the comment — a guard whose comment does not record
the measured bad value is indistinguishable from a guess.
