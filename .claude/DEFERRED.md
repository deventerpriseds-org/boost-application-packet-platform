# Deferred work — the ledger of what is NOT done

**Why this file exists.** Twice in one session, work that was never done read as done. The P3
remediation lane died without pushing and the tracker went on listing it as in flight. An
`actions.md` entry said the "Re-run ATS analysis" button could not re-run months after it was fixed.
Both failures are the same shape: **a claim about state that nothing re-checks.**

Every row below is something a reader could reasonably assume is finished and is not. Each names
**what makes it look done** — because that is the thing that will mislead the next session — and the
**trigger** that should make someone pick it up.

Rules:
1. A row leaves this file only when the work is done AND verified, or when the owner decides it will
   never be done — in which case its status becomes `WONTDO` with the reason, never just deleted.
2. Adding a row is part of the commit that defers the work. Deferring silently is the failure.
3. `git branch -r` is the proof a lane exists. A tracker entry is not.

**This file is machine-checked by `api/test/deferredLedger.test.mjs`.** Prose said "CLOSED" here
while other rows said "DONE" and "FIXED", so nothing could tell open from closed, four IDs meant two
things each, and a bad merge left a section duplicated verbatim. A ledger that exists to catch stale
claims went stale three times. The format below is what makes it checkable — a malformed or stale row
now fails the suite.

**Status** is one of `OPEN`, `CLOSED`, `WONTDO`. It is a token, never inferred from prose. A row with
any part still outstanding is `OPEN`, however much of it is finished — "DONE, but not verified live"
is exactly the claim this file exists to catch, so it is OPEN.

**IDs.** `D1`-`D37` are frozen, the same way `H1`-`H44` are (see `H26`): they are cited from
`.claude/actions.md`, from commit messages and from each other. The counter is retired — **every new
row takes a slug**, `D:two-or-more-words` saying what it defers. Four numbers had already come to
mean two things each (`D20` `D21` `D22` `D26`); the later claimant of each was re-slugged, and a new
numeric id now fails the suite.

**Every `OPEN` row carries exactly one `check:` directive** in its last column, and the suite RUNS it:

| Directive | Row stays valid while | Fails when |
|---|---|---|
| `check: grep <path> <regex>` | the pattern is still PRESENT | it no longer matches — the defect is gone, so the row is stale |
| `check: absent <path> <regex>` | the pattern is still ABSENT | it now matches — the thing was built, so the row is stale |
| `check: manual <vehicle> — <reason>` | — | the vehicle is not one of `db-query.yml`, `api-test.yml`, `ui-verify.yml`, `owner`, `lane` |

There is no fourth kind: an owner decision is `check: manual owner — …`, so it is validated like any
other. Write a literal pipe in a pattern as `\|`; an unescaped one splits the markdown row.

**A pattern must be able to go false, or it is not a check.** Three of the first four written here
could not, and two were proven inert by reinstating the exact regression the row names while the
suite stayed green: `D2` grepped `generalize`, which survives the import, the type literal and a
comment after the last CALLER is gone (now `= generalize\(`); `D10` grepped `H26`, which survives in
comments after the case itself is deleted (now `test\('H26:` — `H26` strips comments before scanning
for exactly this reason, and this check had done the opposite); `D14`'s defect is what `covered_kw`
MEANS, which no source grep can settle, so it is `manual`. An empty pattern compiles to `/(?:)/`,
matches every file, and is rejected.

A `manual` row is not a passing row. It is a row nothing in this sandbox can settle, so it must name
the vehicle that WOULD settle it — absent evidence is `not_applicable`, never `pass`. The census
prints all three buckets on every run — machine-checked, manual, and **closed with no check at
all** — because the first version printed the first two and omitted the third, so 16 rows closed by
prose alone read as covered by a green run.
